# S5.3 MCP 宿主接线与协议核查

日期：2026-09-27。状态：主会话已复核源码，已提交既有 GPT-6 Pro 审查会话；待 Sol Max 完成实施方案核对。本文不是已修复或利用成功证明。

## 确认的生产代码缺口

- Web `main.rs::api_mcp_call` 直接发送 `tools/call`，仅接收 server_id、tool 和 arguments。注释把权限检查交给前端/调用者，但该 handler 没有执行现有工具权限链；不能以按钮确认替代后端授权。
- `api_mcp_server_connect` 从工作区 `.coolzhu/mcp_servers.json` 读取配置，查找 ID 后直接启动，未核对 `enabled`。工作区文件可能被仓库或模型改动，其内容不应自行变成执行授权。
- `McpRuntime` 的全局容器只用 server_id 做键，没有工作区身份；需要避免切换工作区后误用同名旧连接。
- 旧连接使用直接 `Command.spawn`，无托管 Job；初始化失败通过 `?` 返回，未显式收回进程树。stdout 的无界 channel 和无长度限制的 `lines` 允许持续累积；stderr 截取显示字符发生在整行读取之后，不能限制单行内存。
- 此 Web 通道只接 stdio，不应凭其他库声明已完成所有 transport 的生产接线。

## 共享库复用的必要前提

`core-runtime/src/mcp_stdio.rs` 已有进程监督、取消、权限调用入口及消息上限，可以复用其职责，但不能原样转接：`write_jsonrpc_message/read_jsonrpc_message` 默认使用 Content-Length 帧；`request` 将下一条消息作为对应响应，无法正确处理插入的通知或服务端请求。

本项目 Web 握手使用的 [MCP 2025-06-18 官方传输规范](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)规定 stdio 为换行分隔的 UTF-8 JSON-RPC 消息。因此 Content-Length 假服务回环通过，不等于标准 MCP 服务兼容。LSP 的 Content-Length 不可直接作为 MCP 默认格式。

## 最小修复方向

1. 先核对所有既有 MCP 实现/调用者，选共享协议与运行时入口；不增设第三套协议框架。
2. 标准 stdio 使用有界换行 JSON-RPC，区分通知、服务端请求和响应。只有真实调用者需要时才保留显式旧格式兼容，不自动猜测成功。
3. Web 保留现有用户入口，转接受监督的共享服务；后端验证用户授权上下文、启用状态和规范化工作区，手动工具调用同样走现有权限链。
4. 资源绑定工作区和明确生命周期，初始化失败、取消、断线和关闭必须回收；工作区切换后旧句柄不能路由到新工作区。
5. 必要验证包含标准 MCP 服务真实初始化/工具调用、无权限零调用、disabled 零启动、同名跨工作区不串用、通知插入、超限与异常释放。右栏最终操作另存截图。

上述方案待源码复用评估和 Pro 审查收口；不把“拒绝所有请求”作为功能接通，也不把库测试代替用户入口验收。

## Pro 返回与主会话裁决

Pro 审查轮次 `a9b24537-deef-4f5f-8b98-f1e95526f7e5`、补充轮次 `fb56bd5a-e81b-4648-89ac-b54e458fee80` 已返回，认可先修标准传输语义、再复用权限与进程监督、最后接 Web 的顺序。主会话采纳协议分类、工作区归属和异常释放要求，并作以下范围校正：

- Pro 建议保留 `--legacy-mcp-debug` 不是用户需求。本轮不为旧不受控链增加新开关；可删除重复实现并保留对外入口兼容。
- 手动 UI 操作有独立的用户执行上下文，不必假造正在运行的聊天。应复用现有手动执行权限入口；模型调用才继承真实父 run/取消/预算。二者都不能只相信前端传来的权限声明。
- 持久 MCP 服务生命周期与某一次聊天不同；正常回合结束不应无条件杀死闲置且有效的连接。取消在途请求后如协议状态未知，可以停止该连接并要求显式重连，不能自动重放副作用。
- Content-Length 兼容仅在检查到真实调用者需要时保留。不会为假设的兼容场景增加额外配置体系。
- Pro 的“必须接 ChatTurnGuard”不直接套用手动连接；沿用既有资源管理与运行上下文的正确层级，避免增加不必要的聊天锁。

### 模型接线的具体决定

Sol 确认 `llm_tool_definitions_for_session` 原来仅组装内置工具，模型派发最后落入 registry，没有 MCP 生产分支。现有暴露工具名校验、根预算和工具收尾继续复用。用户显式连接后发现的工具可进入默认候选；自定义 `tool_allowlist` 仍限制这些工具，运行时按 `DangerFullAccess` 门禁处理，未知名称不获得默认权限。

模型请求使用冻结的父工作区、聊天室及执行会话，不能用手动调试页面的“当前管理会话”代替发送对象。定义生成时还需冻结连接实例标识，执行时复核，避免同名服务重连后误用新实例。取消或超时后存在响应状态不确定的连接应失效并要求显式重连，不将旧响应交给下一次调用，不自动重放。

实测同时发现小上下文会话把全部 MCP 定义过滤掉：`select_tools_for_request` 在 <=16384 窗口只保留固定内置白名单。上述首次成功使用 65536，不能据此声称 8K 已通过。后续查询实际生效参数，Custom 默认为 64000 上下文/64000 配置输出，经过请求预留规则后实际 max_tokens=32000；此前“默认 8K”的描述不准确。

Pro 补审轮次 `1002cdd4-74b3-40c4-9978-e62d154ffbf8` 与主会话确认：修现有候选选择点，不取消小窗保护或新建工具路由器。只考虑上游已发现、已通过 allowlist 的 MCP 定义；确定排序，优先已有调用链所需项。最多 4 个/估算 1024 tokens 可作为额外上限，还必须受实际剩余 prompt 预算约束。现有上下文预算未计工具 schema，故不能在已经填满的历史后固定加 1024。需计算 system、消息/图片、输出预留及已选内置 schema 后的余量；图片沿用图像估算，不按 base64 字符数估算。被裁剪的事实须可见，不承诺所有连接工具必然暴露。
