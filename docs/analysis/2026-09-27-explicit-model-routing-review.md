## 已复现的产品缺陷

Sol Max 在独立临时环境创建 Custom 会话：`model=s0-image-text`、显式 `model_type=text`，再保存 `supports_multimodal=false`。读取配置得到 `effective_supports_multimodal=false` 与 `image_input_strategy=vision-description`。向真实聊天入口发送 1px 合成 PNG 后，没有任何 provider 请求或请求轨迹，却得到 `assistant-fallback`：“图片生成失败：会话未配置 API Key”，持久化 run 状态为 `completed`。

原始复现留在本机 `tmp/s0-controlled-replay-20260927/runs/a51324ccfc5f/media-name-probe.json`。执行 Web SHA-256 为 `A55CD7ED616728211FCE93F4239ED2FBE128687EBBA09FDB15FB2984A46E521B`。主会话已读取复现和源码；这不是模型能力不足，也不是更换假模型名称即可关闭的测试问题。

根因：`agent_media_gen_kind` 先读已保存的类型，却仍以逻辑或叠加模型 ID 的名称推断；`resolve_model_type` 对 `image`、`video` 做子串判断。流式入口在图片准备之前进入生成分支，因此图片理解能力的明确设置无法控制该次路由。生成帮助函数又将业务错误封装为消息，调用方直接继续循环，没有将失败传播为运行失败。

## 主会话与 Pro 的路由裁决

原“整合审查执行计划”会话实际返回《模型媒体路由窄审查结论》，同意：执行阶段尊重已保存的明确模型类型，名称推断仅留在新建缺省及旧记录缺失字段的兼容入口；不增加 provider 表、另一套运行器或大规模迁移。

输出生成协议和图片输入能力分别判断。`supports_multimodal` 当前已验证契约是图片输入，不由字段名称推称视频输入已实现；该开关为 false 也不能直接禁止一个明确设置为 image/video 的生成会话。主会话不采用把这两种语义混成单一能力优先级表的扩展建议。

旧数据兼容必须按真实加载路径处理：JSON 缺少类型时当前默认 text，SQLite 类型读取失败才按名称推断，DTO 还有归一化。窄修应能区分缺失兼容与已保存的合法 text，不能运行时再次依据名称覆盖明确值；不得为修复而批量改写用户旧数据、URL 或密钥。

## 实施与验证边界

已交专门的 GPT-6 Sol Max 子代理实施路由窄修；本次只解除相关模型类型解析和必要验证文件的冻结。视觉、LSP、导航等不借此改动。021 的安装版实操继续，新源码的结果和后续新包身份分别记录。

最少验证包括：显式 text 配合含 image/video 的名称仍走聊天；显式 vision/multimodal 配合 image 名称仍走理解；显式 image/video 配合普通名称仍走生成；图片开关 false 的文本目标确实调用默认视觉转述；缺省创建及旧 JSON/SQLite 类型兼容。使用受控端点核对实际请求，而非只检查函数返回。

生成失败被记 completed 的状态传播也已收到 Pro 的第二轮回复《媒体路由 + 失败状态语义窄审结论》，双方同意在同轮修正。采用结构化成功/失败事实，由流式和非流式入口消费，禁止解析中文错误文案决定状态；取消与超时的既有终态优先规则不改变。异步视频的已提交、待处理与产物完成必须先按现有契约核实，只修明确错误路径，不把正常 pending 判为失败，也不把提交成功写成视频已生成。两轮原始页面记录留本机 `tmp/2026-09-27-pro-model-routing-review.*`。

主会话另收紧回复中“没有 provider 请求就不能显示生成失败”的表述：缺 Key 等前置失败当然可以如实显示为配置错误，并记录 failed；不能制造已发出的请求或计费用量。无需为了填充轨迹而发起本不应发生的网络调用。实现与复验尚未完成，审查同意不等于缺陷关闭。

六类回放的正常名称正例仅证明相应分支，不覆盖冲突名称。该确定缺陷修复并复验前，不能把六类整体标成全部通过。
