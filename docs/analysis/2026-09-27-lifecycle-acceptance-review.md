Goal 已有真实 phase/run/claim、工作区和根预算，当前缺子执行所需配置快照及运行数据库路径。应在既有接纳处补快照，复用 HostAgentRunner；子请求/工具校验 live claim，停止或租约丢失后不能再产生新业务动作。优先复用已有取消通知；如使用数据库监视，应限于该 phase 的生命周期并可靠结束。

## DATA-01 与应用 PKG-01

Pro 将 PKG-01 讨论成插件事务，主会话校正：本报告 PKG-01 是 MSI 应用打包安装。插件安装事务已经独立验证，不可替代应用升级恢复证据。

隔离样本至少包含两个会话、中文历史、附件元数据、运行状态及秘密引用。使用实际备份/迁移/恢复路径检查正常升级后数据语义一致、事务中断无半迁移、备份可恢复、旧程序面对更高 schema 明确拒绝且不改写。不要对用户真实库做故障注入。

秘密保护需分别记录同用户 DPAPI 恢复和跨设备可恢复条件；不能把无法跨设备解密当作恢复成功，也不能在报告输出秘密。新 MSI 安装前后核对包身份、已安装版本/二进制、用户数据保留以及可打开的实际界面。旧包的哈希不能证明新包内容。

### DATA 隔离实测发现（2026-09-27，修复中）

- 构造真实 v26 结构后，正常迁移与备份恢复保留了三个会话、中文消息、附件元数据和 completed run。活动 SQLite/JSON 原始字节未检出测试用假秘密；迁移前备份保留原假明文，不能把备份描述成已清除历史明文。
- 高版本库 `user_version=99` 被拒绝启动，但文件 SHA256 改变。源码证实两个打开入口均先执行 `journal_mode=WAL`，再检查 schema。修复须在任何此类设置写入之前检查版本，并实测拒绝前后库文件不变；已有 WAL/hot journal 的打开行为需独立界定，不能只靠主库版本值未变宣称完全未触碰。
- 自建聊天室原有两条消息在启动后被复制到默认聊天室，总量变成四条。`migrate_session_messages_into_default_chat_room` 仅在默认房间去重，未识别消息已属于其他房间。拟按所有房间的稳定消息 ID 识别已有归属，仅回填真正孤儿的旧 session 消息。原弱签名不包含时间和附件，不能扩展到跨房间去重而丢掉合法同文消息。
- 上述均为真实反例，修复与复验尚未完成；已送现有 GPT-6 Pro 会话进行聚焦风险复核。

Pro 首轮 `29c76aee-c8ed-4135-86ac-fbe785516702` 认可提前版本检查并共用打开顺序。主会话补充限定其“读取本身安全”的判断：[SQLite 官方锁说明](https://www.sqlite.org/lockingv3.html)说明读库前可能恢复 hot journal，[WAL 说明](https://www.sqlite.org/wal.html)也提示只读连接的共享内存文件条件。因此当前 clean 高版本反例修复不自动证明所有崩溃库字节不变；不得用 immutable 忽略 WAL，也不应在未知高版本库上自动尝试恢复。复验须记录实际主库及 sidecar 状态。

消息回填补审轮次 `de8f1dc7-31e8-4ec8-bce1-00820717af85` 认可按稳定 ID 检查所有聊天室，反对弱签名全库去重。主会话不采纳为此新增迁移状态表的建议：本次只防止新增错误镜像，保留现有 ID 和数据，不清空或自动删掉用户已有的疑似重复历史。已落盘代码使用既有房间消息事实，正在编译复验。

数据库修正使用现有文件的只读版本预检，之后读写连接再次检查版本，再设置 WAL。无法只读打开的未知恢复现场应明确报错；这可能使需要 hot-journal 恢复的旧库要求单独恢复处理，不能用无条件读写回退来掩盖边界。正常 WAL 重启由持久任务现场另验。

修后源码构建 `dfd39612cd2d689e6cf4e87de9b0c421682d1be33137d854a4ce8f5d2479d8ce` 已完成正常迁移/恢复及 clean v99 拒绝实测：数据数量和归属保持一致，主库哈希不变，WAL/SHM 前后均不存在。备份位于同工程 `.coolzhu/schema-backups`，本机样本 ACL 与源库一致，仅 SYSTEM/Administrators/当前用户；打包脚本排除数据目录、备份及 SQLite，未发现自动诊断导出该备份的路径。旧备份忠实保留旧假明文不定性为新增漏洞，也不宣称已加密；本轮不新增备份格式。

## JOB-01

在独立工作区和端口运行实际持久任务，记录 occurrence、claim、执行 attempt 与真实副作用计数。在已接纳/执行中的代表性窗口停止隔离服务再重启，核对同一 occurrence 不被静默重复派发、旧运行状态可解释。仅观察日志或手工把状态改成 completed 不能算通过。不需要为这个场景重启用户操作系统。

上述同一构建的真实 HTTP 实测已确认：首任务 settled，第二任务执行中终止隔离服务后重启，同 occurrence 保留 running，重新触发返回 unknown 且不再调用模型；受控模型收件数保持两次。它证明防重派，不证明执行结果已恢复或外部副作用恰好一次。

实际右栏确曾误显示“1 项待执行”。修复后的 `8969352151eae80d12e15cccd2bf65e0508f99d73b192eb8b80ae0705bf92e44` 构建以一次只读连接及精确 occurrence 查询投影领取事实，未创建缺失执行库，也不自动重领或改写配置状态。读失败显示状态暂不可用；已有领取计为待核对。主会话已查看 [修复截图](../testing/release-0.2.17/evidence/lifecycle-source-e2/job-unknown-after.png)，确认显示“0 项可执行 · 1 项待核对”与“已领取，执行中或中断后结果未知，未重复执行”。这项源码版 UI 验收通过，新 MSI 安装版仍需独立核验。
