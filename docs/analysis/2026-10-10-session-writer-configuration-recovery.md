# 会话库写者与配置恢复接线

现有 `SessionStore` 在进程内用 Mutex 保护全量缓存保存，但 SQLite 自身的事务锁不能阻止另一个 Web 实例先加载旧缓存、之后整表重写。启动恢复在 HTTP 监听前运行，单纯依赖端口冲突也不能保护另一端口的实例。

候选 `session_writer.rs` 使用库路径旁的固定锁文件及操作系统文件锁，持有者由 `SessionStore` 的 Arc 保持。同进程相同规范路径的工程重载复用句柄；换到其它库后释放旧库引用；进程异常退出由系统释放。Windows 锁文件持有期间禁止删除，文件本身长期保留，不能以删除旧锁文件恢复资格。启动只读解析配置以确定实际库路径，取得锁后才写默认配置、迁移凭据、nonce 和恢复运行记录。工程切换先取得目标库所有权；失败返回409，不撤销当前LSP/终端或切换工程。

同一数据库的既有 metadata 表保存 `session_writer_epoch`，新持有者在 IMMEDIATE 事务内递增。同进程重载不重新领取。缓存保存以 IMMEDIATE 事务核对当前 epoch，再写数据；全量 metadata 清理保留该键。旧 epoch、损坏值或溢出不允许提交。epoch 是私有持久化控制身份，不放入公开 RunIdentity，也不冒充桌面 input owner epoch 或运行 claim token。

该候选覆盖 Web 实例的会话库所有权与缓存保存 fencing；不能声称所有独立宿主、所有原生输入资源或配置/SQLite跨资源事务已经完成。需要统一迁移入口、模块写入和后台恢复共同遵守原工程活动 pin。普通旧版 EXE 尚无该锁，混用旧写者不在当前代码可保证的范围，验收时需按真实实例身份核对。

统一会话配置的崩溃日志已接入候选，详见 [配置崩溃恢复说明](2026-10-10-session-config-crash-recovery.md)。其协议复用同一库与配置发布，不创建第二份会话系统：在参数发布前保存受保护的旧配置及操作身份；SQLite 会话更新事务同时写提交标记；重启取得写者后，根据标记保留已提交配置或撤销未提交配置，处理前不启动worker。凭据不能以明文进入恢复记录。其它配置写入在未解决操作期间不能覆盖恢复前像；恢复碰到不同配置摘要应明确停止并保留证据。现有同进程版本CAS与失败回退不能代替这项崩溃协议。

验证计划覆盖两个真实独立测试进程竞争、崩溃释放、同进程重载、持久epoch递增/旧缓存拒绝；再用隔离工作区运行真实EXE双实例/工程409/重启恢复。模块测试只证明对应行为，不替代统一批次正式安装实拍或跨资源故障验收。
