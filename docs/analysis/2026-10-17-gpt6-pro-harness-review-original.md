## 三、最小实现应遵守的几个边界

### 1. 复用已有权限链，把“可看见”“曾获准”“现在仍获准”分开

现有 `HostModelSnapshot` 与 `model_tool_host_preflight` 已提供重要基础：前者约束接纳时的上限，后者还会查询当前工具定义并在 hook 后再次执行。**不要让 `FinalRequestSnapshot`、TaskScope 或审批缓存拥有另一个可独立放行的权限副本。**  
**证据：**`W/host_child_agent.rs` L70、L109；`W/main.rs` L35245、L35257、L35294。

最小调整可以是：

- 请求对象记录本次实际模型、有效参数、最终工具声明和关联身份；已有字段能复用就复用。
- 授权仍引用现有宿主记录；缓存只帮助判断是否需要再次询问。
- 新的明确授权由新的请求接纳，不能事后改变旧响应的调用资格。
- 撤销、取消、工具停用及实例更换在执行入口生效。

“实时生效”的验收口径必须具体：**撤销已被宿主接纳之后，不再允许尚未开始的相关操作领取执行资格。** 已经开始的操作按工具能力取消，并保留实际或未知效果；不能把“停止等待”描述为“效果已撤销”。

对竞态的最小要求，是让最终执行资格判断与撤销接纳有明确先后顺序。优先使用现有执行登记、版本或局部同步机制；不要跨模型请求、人工审批或长工具运行持有全局锁。包内尚不足以确认所有底层工具已达到这一保证。

### 2. 保持活跃任务连续性，不建设新的任务语义审批流程

建议将 T03 缩为**已有任务/运行身份上的轻量连续性信息**：

- 原始用户请求的消息引用。
- 仍未完成的目标，以及已有完成证据。
- 用户后续补充、收窄、暂停、取消或替换的可信消息引用。
- 当前有效授权的宿主引用。

状态追问不清空原目标，补充要求不抹掉已经完成的部分；真正扩大的动作范围另行判断是否已有授权覆盖。对于已结束的旧任务，则不默认恢复。

不建议每条新消息先发起一个“续接、替换、授权分类”的模型请求。普通语义衔接可由当前执行模型处理，**授权是否成立必须由宿主来源与执行规则决定**。

尤其不能把这些内容当成授权：

- 摘要中写着“用户已经同意”。
- 工具结果要求继续执行。
- 子代理声称已获许可。
- 角色为 `user` 的合成上下文。

DSH 的 `hasDirectHumanInput` 检查的是当前根 Agent 开放回合中是否存在特定来源事件，并不分析某个具体动作是否获得用户许可。它不能直接替代 coolzhu 的动作授权规则。  
**证据：**`D/goal/tool-goal/src/authority.ts` L80、L83、L100；`D/goal/tool-goal/src/index.ts` L222、L224。

### 3. 请求重试、效果重放、轮询和无效循环必须分别处理

**请求重试：**针对模型请求或传输失败。必须限制尝试次数与总期限，并保留失败阶段。不得再次接纳同一用户输入，也不得把已经执行过的工具当成新工作重放。DSH 的首次接纳控制可借鉴，但其外层重试并非始终复用完全相同的环境快照。  
**证据：**`D/core/agent-loop/src/agent.ts` L410、L426、L441、L526。

**效果重放：**同一个逻辑操作因断流、重连或回执丢失再次到达。优先查询原执行身份和回执。若效果未知，应进行针对性核查，不能通过换 ID、换工具名或重新请求模型把它变成“安全重试”。对于外部非幂等操作，单靠本地登记不能自动保证端到端恰好一次。

**合法轮询：**相同参数可以连续返回运行中，也可以最终返回完成。在合理等待范围、任务仍存活且调用本身是等待/查询时，即使结果暂时不变，也不应要求模型换方法。优先使用长等待或状态订阅，减少每次状态查询都再经过模型。

**无效循环：**相同失败重复出现，相关状态、输入和处理策略都未改变，且不属于合法等待或有依据的有限重试。此时才提示具体阻塞或让模型做一次有目标的修正。输出时间戳变化也不能被当成有效进展。

因此，L1 最小修复应从**取消绝对断言和错误动作指令**开始，而不是立即建设一个能判断所有任务语义进展的检测器。

### 4. 验证先确定执行者和证据含义，再考虑缓存

T07 最值得先做的工作是**避免模型与 runtime 无理由执行同一项验证**：

- 当当前 Goal 明确配置且启用了 Command 验证时，指定谁负责执行、谁消费结果。
- 若模型为诊断已经执行了相同验证，并且宿主能取得可靠执行回执，可以提交这份证据。
- 若回执条件不足，不能拿模型文字替代；此时由 runtime 执行，并避免再指示模型机械预跑一遍。
- 普通聊天和简单修改，不自动套用 Goal 的多角色验证链。

当前 `Vec<String>` 返回值不足以支持安全复用。应先明确区分通过、失败、跳过/未要求，以及无法执行；对已有明确验证合同，读取异常不能被当作通过证据。  
**证据：**`W/main.rs::run_goal_phase_command_gate` L48183、L48186、L48189；`goal_phase_command_failures` L48147、L48162。

**证据可以复用的前提**是：证明对象、验证合同和相关输入没有变化，且证据来自可信执行。至少应考虑命令及参数、cwd、实际文件内容、测试和构建配置、依赖锁文件、工具链及相关环境设置。这里的“相关”应由检查本身决定，不能每次全仓计算一套新指纹。

**需要失效或重新判断的情况**包括：

- 相关代码、测试、配置、依赖或验证标准发生变化。
- 验证期间有相关并发修改，无法确认验证对应哪一份内容。
- 环境或外部状态变化会影响结果。
- 记录不完整、结果未知、未真正执行。
- 用户明确要求重新验证。

**不应仅因状态追问、摘要更新、角色切换或 TaskScope revision 增加而重跑构建。** Git HEAD 没变也不代表文件没变，本次 coolzhu 本身就是 HEAD 加工作区快照。

FilesExist 这类廉价检查通常直接复查即可；缓存它可能比检查本身更复杂。任意 shell 命令、联网集成测试、依赖外部状态的检查也不宜纳入通用缓存。

## 五、最先实施的五项

### 1. 修正通用指导和活跃任务连续性——T02＋T03 的小范围部分

先处理最后一条 user 覆盖活跃任务、Goal 重复指导、无条件写后再读，以及不考虑已有授权的确认措辞。

这项不应等待完整 TaskScope 框架。优先验收“状态追问后继续原目标”“已有批准不再问”“已取消任务不恢复”。

### 2. 调整工具暴露，并绑定实际请求——T04＋T01 的最小部分

为明确选定的能力配置移除动作关键词硬门，保留基础工具与可用发现入口。同时让 SSE 首响应及后续派发引用实际发送的工具集合。

不能通过扩大权限、忽略显式禁用，或一次塞入所有 schema 来实现这一项。

### 3. 修复 L1 与明确无收益的文本恢复——T06

这是当前证据最具体的一项：相同参数被错误断言为无进展，而且第二次工具可能已经执行。

先修改断言与触发条件，再将确定终态的机械回复交给宿主。保留可修复问题所需的正常模型回合。

### 4. 拆开优化审批交互和 Web 调度——T05 的小范围部分

先避免同一逻辑调用在 hook 前后重复询问；若有并发重复审批，再复用现有 pending 记录解决。调度从已知安全读取和明确独占资源开始，不以一次统一 Web、CLI 和所有插件为目标。

### 5. 明确验证结果，指定验证执行者——T07 的前半部分

先解决“空失败列表的含义”和“同一验证由谁执行”，再增加当前任务内的有限证据复用。不要把第一版交付目标设为跨会话、跨工程的验证缓存。

上述改动应同时补充必要观测字段，不必先建设独立观测平台。现有模型请求已经标记了 `chat`、`tool_feedback`、`child_agent` 和 `text_recovery` 等用途，可以优先扩展这些入口。  
**证据：**`W/main.rs` L27996、L35611。

## 六、明确不建议实施的事项

1. **整体替换 DSH 或 Codex 主运行时。**当前材料支持局部借鉴，尚未证明整体迁移能以可接受成本解决这些具体问题。

2. **将 FinalRequestSnapshot、TaskScope、审批缓存和验证缓存分别做成独立持久状态系统。**会增加多处写入、恢复、失效及竞态处理，现阶段缺少必要性。

3. **每条消息先做独立模型分类，每步先规划/审批/验证一遍。**这会直接增加模型请求，也把原目标中的自主性问题带进新架构。

4. **以相同参数禁止再次执行，或要求模型更换工具名规避重复检测。**轮询、再次观察、有限重试和效果重放需要不同处理。

5. **缓存命中后跳过当前授权、取消或实例有效性检查。**缓存应减少询问或重复计算，不能创造继续执行的权限。

6. **仅按 Git HEAD、任务 revision、命令字符串或固定 TTL 复用验证。**这些单独都不能证明验证输入未变；也不能仅因时间经过或状态追问而作废仍有效的证据。

7. **把 `failures.is_empty()` 直接写成缓存成功条件。**先明确有没有执行、是否要求执行、执行结果是否可核验。

8. **无条件关闭必要验证、全部恢复、全部读取复核，或统一降低 reasoning effort。**这些做法可能只把成本转成失败、漏做和后续返工。应优先减少无收益调用。

9. **默认开启多代理、PTC、无限重试或“同一阻塞必须重复若干轮才允许停止”。**确定不可恢复的阻塞应可以直接报告，不需要为了满足计数而再失败几次。

## 七、仍需实测的事项与可采集指标

**下面是拟定验收判据，不是本轮已经取得的测试结果。**

### 1. 工具暴露与提示词调整是否改善任务完成

使用同一模型、版本、effort、工具实现和任务材料做配置对照。覆盖纯聊天、需要查证但无动作关键词的问题、单文件修改和多文件任务。

采集任务验收结果、首次有效动作时间、模型请求数、工具数、额外确认次数、输入 token 与实际缓存 token。不能把提示词变短直接解释为推理变快。

### 2. L1 是否正确区分轮询与空转

覆盖同参数持续运行、进度变化、最终完成、永久失败、外部状态变化后重试，以及只有时间戳变化的输出。

验收要求：合法等待不出现错误“换方法”指令；永久错误有界结束；无关输出变化不能伪装有效进展。

### 3. 断流、超时及 post-hook 失败是否导致效果重放

使用能明确观察效果次数的工具样例，在效果发生前后分别制造故障。采集逻辑调用身份、执行入口次数、回执状态和实际效果次数。

验收要求：已经产生的同一逻辑效果不再执行；未知效果不能被标为未执行或成功。现有 `model_tool_calls_executed` 布尔值不足以单独充当真实执行次数，因为共享循环在派发返回后就将其设为 true。  
**证据：**`W/main.rs` L28072。

### 4. 并发审批与撤销是否正确

并发制造相同会话授权范围的缓存未命中，分别在审批等待、hook 执行、工具排队和执行开始前撤销。

采集本地复核次数、真实用户审批交互数、自动审核模型请求数、撤销接纳时间及执行开始事件。

验收要求：允许共享的会话级授权不重复打扰；一次性批准只覆盖其对应调用；撤销后尚未开始的相关动作不能继续领取资格。

### 5. 验证证据是否既复用又及时失效

覆盖无变化再次完成、同一 HEAD 下修改代码、修改测试或锁文件、改变参数/环境、验证时发生并发修改，以及关闭门控、空命令和读取异常。

采集验证实际启动次数、执行结果状态、证据引用、失效原因。无相关变化时不重复相同检查；真实相关变更后不得消费过期证据；未执行不能记为通过。

### 6. 并发和 T08 是否值得继续

分别统计工具排队、执行、模型等待、审批、退避和验证时间，并观察 Web 插件宿主的 `HOST_BUSY`、同资源冲突及父模型等待。

只有数据证明父等待或多次小工具往返占主要成本，才扩大异步子任务或 PTC。比较并发耗时必须看重叠和关键路径，不能简单把所有阶段相加。

**统一报告口径：**先报告真实验收结果及失败原因，再比较成功任务的总耗时分布；人工等待单列。推理 token 未由提供方返回时记为未知。样本不足时列逐次结果，不给稳定的 p95 或提速百分比。
