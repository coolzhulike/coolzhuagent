# Browser中间进展的后续方案（尚未实施）

正式120/121长程证明实际三阶段输入可用，但当前native_browser_verification::visible_progress把任意nodes变化当中间进展，外层行情每100ms刷新也会清零无进展计数。最终成功仍走grounded criteria，不能因此外推完整3.4或把中间effect_observed当动作因果已经证明。

直接忽略全部StaticText不是可用修补：普通AX快照不带编辑值，text_input的实际变化可能不在nodes；随后Enter只新增局部验证文字，在默认连续两次无进展上限下，正常多步表单可能误停。放宽上限、把ACK/sent当效果或从上一动作反馈推出当前效果都不可取。

按当前职责划分推进：

1. 原生宿主负责只读确认编辑前后状态。已有native_browser_editor::READ_EDITOR限制普通text/search/textarea、聚焦/可编辑、值4096；native_browser_edit_input最后前置读取后只发一次Input.insertText。后续复用固定读取与原节点/文档绑定，仅报告本次请求的目标值是否按实际插入改变；原值/选区不进入模型或通用日志。投递ACK继续仅投递事实。
2. 适配器复用现有Mutex<PageProvenance>及SettledInputSource.input_request_id承载本步效果来源，不新建权威账本/第二把锁。效果证明只能对应当前动作、同冻结宿主/工程/聊天室/资源，变化失配回未知而非扩大权限。
3. 中间进展依据实际目标控件状态、正确文档滚动/导航、或宿主确认的本步编辑效果；最终任务完成继续全部grounded criteria。纯行情/未相关文字刷新不得置effect_observed或清零无进展。控件焦点变化只算本步聚焦准备，不能证明文本目标。
4. 控制器继续使用既有ActionReceipt、Verification及RunBudgetGuard；区分本步目标效果与任务标准，不从累计旧成功推导当前进展。实现前须核清实际回执投影点，避免只改提示而保留事实误报。

兼容与风险：协议只增加有界效果事实时，旧宿主缺字段必须为未知；认证请求ID及源资源不可省。读回失败不重放输入、不延Browser2/5秒或900秒预算。状态归因只能证明目标编辑/滚动变化，不能保证网页业务接收；业务仍要独立标准。跨URL/新原生Target及HRESULT严格竞态验收不由此关闭。

验收沿用真实SWE-2/唯一island：一项多步表单正例跨来源动态行情+插件后续；一项目标不变化但行情刷新反例，必须不冒进展且按既有上限结束。保留软件原图、可信输入、每步投递/释放/效果、根终态和唯一会话解锁。仅必要边界逻辑回归，不新建模型夹具。当前先完成多行引文误拒修补候选，本文不代表实现或正式通过。
