# 高风险待决策项登记

状态：这些事项**需要产品/安全/运维判断**，本轮及之前的几个增量都刻意没有自行决定。每条都写清：现象与证据、不决策的后果、我们的临时处理、以及决策影响面。
依据：计划 §2.2 / §2.3 / §2.4 / S1.4 / S2.1 / S2.4 / S2.5。

配套文档：**未完成项与风险清单见 `risk-open-items.md`**（本文只回答"哪几件必须由人拍板"，那份回答"还有什么没做完、风险是什么"；两份按 D-x 编号互相引用）。

## D-1 未确认释放时，是否再由本进程补发一次独立释放

- **现象**：native helper 在 `input_stroke_native.cs` 的 `finally` 里捕获 `driver.Up()` 失败并抛 `mouse_release_failed`（自己已重试 3 次）。此时左键**可能仍处于按下状态**。
- **当前处理**：已实现的是"helper 被强杀 / 自己非零退出且没给原因"时由本进程补发；**helper 明确报过失败时不再补发**（维持既有语义）。
- **不决策的后果**：罕见情形下鼠标左键保持按下，用户的后续点击会变成拖拽。
- **补发的风险**：只发 UP、不移动光标，看似安全；但它会改变既有语义，且若 helper 的失败源于驱动异常，补发可能同样无效——需要产品判断"多补一次"与"保持现状"哪个更可接受。
- **影响面**：`input_stroke.rs`（`needs_emergency_release` 的一个条件）+ 一条回归。

## D-2 本地模型端口绑定的副作用（agent 退出会停掉 bonsai）

- **现象**：为了让 agent 把 bonsai 识别为"本地模型"，`local_chat_port` 必须等于 bonsai 的 8080（识别条件见 `is_local_model_endpoint_on_port`：本地地址且 URL 含 `:<local_chat_port>`）。
- **副作用**：agent **正常关闭**时会按端口清理，连带停掉 bonsai；调试期的强制杀进程不会触发（已实测）。
- **不决策的后果**：用户关闭 agent 后本地模型服务消失，需重新 `start.bat`。
- **另一选项**：不绑 8080（保持 8082），代价是 agent 不把该会话当"本地模型"（不做品牌化、不用本地上下文预算）。

## D-3 按 provider/会话关闭工具（本地模型长任务的前提）

- **现象**：`[tool] dev_open_permissions = true` 会让 `llm_tools_enabled()` 提前返回 true，**使 `enable_llm_tools = false` 失效**并强制 exposure = "all"；27B 面对"写文件"会去调 `computer_use_perform`，被熔断阻断而拿不到产物。
- **当前处理**：S1.4 已把该耦合解耦（显式配置不再被 dev_open 单向覆盖），但**"只对本地模型关工具"仍做不到**——`computer_use_tool_definition()` 在任何 exposure 模式下都会暴露，除非全局关掉 `[computer_use] enabled`。
- **需要决策**：是否引入**按 provider/会话**的工具开关（需把 provider 身份传进 `llm_tool_definitions_for_*`，属一次小重构，调用点不多但被多处测试锁定）。
- **影响面**：云端 agent 的工具能力 vs 本地模型长任务可用性，二者当前互斥。

## D-4 `partial=true` 的"部分路径恢复"目前是空转规则

- **现象**：§2.2 规定 `sent＋partial=true` 时"停止原路径、确认释放与当前画布、不能整段重放"。但唯一有结构化回执的 helper（受控桌面笔画）要么整段成功（写死 `partial=false, path_completed=true`）、要么返回 `Err`（不生成步骤事实）——**没有任何 helper 会产出 `partial=true`**。
- **不决策的后果**：为该规则写的防护没有产生者；若后续接入会报部分完成的 helper，需要先补齐"确认释放与画布"的实际动作。
- **需要决策**：是否存在/将接入会报部分完成的 helper（MCP/插件工具？），以及那时"确认当前画布"由谁执行。

## D-5 S2.1：`saved→resolved→wire` 的密钥三态默认

- **规范原文**：§2.4"保持/替换/明确清空密钥是三种操作；**空表单默认保持**"。
- **需要确认**：UI 空表单是否确实"保持"而非"清空"——这决定用户改配置时会不会静默丢 key。现行为需产品确认后固化，并配"不漂移"回归。

## D-6 S2.4：切换权威 writer 需要停机窗口

- **规范原文**：§2.4"按会话切换权威前先停写、排空 run、备份并验证基线，拒绝旧入口继续独立写"。
- **需要决策**：可接受的停机窗口与谁执行切换（运维决策）；在此之前不能开始"单写者 + outbox"的接线，只能先做 fixture 与纯逻辑。

## D-7 S2.5：CLI 改真流式的兼容边界

- **规范原文**：§2.5 要求 CLI 不再"靠一次返回 Vec 模拟流式"。
- **需要决策**：CLI 既有输出契约（脚本/管道消费方）是否允许改变；如不允许，需要兼容层与版本化开关。

## D-8 未签名发布与上游历史缺失

- **现象**：四个 MSI **全部 `signed=false`**；0.2.12/0.2.13 的源码提交未获得；上游完整提交历史与 CI 结果本机没有（只取了 `main` 的 tar 快照）。
- **需要决策**：是否引入代码签名（需要证书与发布流程），以及是否改为可追溯的 git 克隆/镜像流程以获得完整历史。
- **影响面**：S0.1 的"发布身份"只能做到"部分完成"，且 SmartScreen 会对用户提示来源不明。
