## 1. RD4-02：独立共享输入安全库（选 A）

### 1.1 三层的分工（不可合并省略）

| 组成 | 负责什么 | 不能代替什么 |
| --- | --- | --- |
| 输入所有权与执行者监督 | 排他输入、在途执行者身份、停止与静止核查 | 不能自动保存进程死亡后的未决安全义务 |
| **用户级共享安全库** | 隔离、未清偿义务、恢复状态、**跨工作区可见**阻断 | 不能仅靠一行 `safe=true` 证明物理状态 |
| 会话／运行事实库 | 原动作、回执、终态及其来源 | 不能要求新 workspace 逐一遍历所有旧库后才知道当前资源是否被隔离 |

**选 B 的错误理由已更正**：不是"同库违反跨库原子性"，而是 **B 不满足"用户级共享资源持久化边界"**（把阻断放回各会话库，无法自然提供跨 workspace／跨实例的统一资源状态）。

### 1.2 固定路径与版本（不得改用）

```
根目录： ResolvedLaunchPaths.input_safety_state_root = <user_state_root>\input-safety
数据库： <input_safety_state_root>\input-safety.sqlite3
```

**禁止**：`<workspace>\.coolzhu\input-safety.sqlite3`、当前工作目录下的库、从 `log_dir` 再次推导的目录、测试夹具路径作为生产默认。
**版本**：本库用**独立的组件 schema 版本**（初始 1）；**不**把主会话库的 v23 改成 v24，两库不共用版本号；会话库若确需恢复关联字段，另按迁移目录统一分配。**文件名稳定**，升级 schema **不得**另建空的新版本文件来遗忘旧事故。

### 1.3 最小持久化实体（授权实现；已有等价机制可复用，不要求一项一张表）

存储身份与版本（`store_id`、schema 版本、初始化状态、与用户级根的绑定）／资源状态（resource scope、状态、revision、当前协调实例·epoch、是否接受新输入）／输入执行登记（action·helper 身份、执行阶段、可能产生的释放义务、最后已知事实）／阻断事件（incident ID、资源 scope、原因、原运行引用、未决·已恢复状态、证据引用）／恢复操作与意图（recovery ID、来源库与旧 run、当前阶段、前置检查、目标 revision、提交结果）／**追加式安全事件**（状态变更、恢复决定与失败记录，用于解释投影与重启对账）。

**不复制**普通聊天正文、模型参数与密钥。历史工作区缺失**仍保留缺失**；来源数据库标识**不是**补造的 workspace ID。

### 1.4 谁写入（技术落点）

- **唯一逻辑写入口**：`InputSafetyStore`／输入安全服务；跨进程写入由统一排他 + 短事务串行化。
- 领域契约放**现有核心/CU 契约层**；Windows 锁与执行者监督由 **`windows-process-guard`** 承担；SQLite 实现放**现有 Web/宿主适配边界**（复用既有 rusqlite）。
- **不把 rusqlite 引入 core-runtime**；**不新增**第二个 Agent 运行时、常驻 Node 宿主或独立 Windows 服务。
- "单一写入者"＝一个逻辑写服务 + 同一时刻受控的实际写者，**不要求**引入永不退出的守护进程。
- **所有正式输入入口都必须经该服务检查状态**；不得一个入口查共享库、另一个入口只查旧 turn 级 SQL。

### 1.5 `resource_blocking_refs` 从字符串变成**可验证关联**

序列化层可保留字符串以兼容既有事实，但**生产接纳不得只检查非空**。每个被采用的引用至少验证：属于已确认的 input-safety store ＋ incident 确实存在 ＋ scope 与本次受影响资源匹配 ＋ 当前状态确实阻止新输入 ＋ revision 与恢复上下文一致 ＋ 与被处理运行·风险有可解释关联。

`"input-safety:incident-9"` 这类测试值**不得**进入生产；删除、已解决、其他 scope、其他 store 的引用均不满足前置条件。允许增加**由服务产生的已验证引用包装/证明对象**（复用既有类型名）；**禁止**调用方通过反序列化 `validated=true` 获取它。若现签名只能收 `&[String]`，可保留底层结构，但**生产入口必须改为接收可信协调上下文**，或**在同一服务内完成真实核查后**调用；**不得**为"保持公开 API 不变"而保留**可自证**的生产入口。

### 1.6 生命周期政策

| 项目 | 决定 |
| --- | --- |
| 首次初始化 | 在实际运行用户上下文建立；**有旧 CU 数据时，初始化 ≠ 资源已安全**，仍须完成旧状态核查 |
| 文件丢失／损坏 | **已登记过 store 身份后不得静默建空库放行**；进入维护／恢复状态 |
| 备份 | 一致性数据库备份，附 store 身份、schema 与恢复意图状态；**跨库恢复仍须单独协调**（一次备份成功 ≠ 整体恢复点一致） |
| 清理 | 首期**不自动删除**未决事件、恢复意图或仍被引用的证据；已解决记录本轮也**不新增自动 GC** |
| 磁盘不足 | 停止接纳新普通输入、保留必要受限收尾；**不能**删除未决记录腾空间后继续 |
| MSI | 安装程序与资源；**不随包放一份生产"空安全库"**；升级／修复／重装**不能清除**用户事故状态 |
| 回滚 | 不让不理解新安全状态的**旧 writer 直接接管**；**不删除**安全库来恢复可用性 |

## 2. RD4-03：宿主签发资格、跨进程、按**实际输入资源**暂停

### 2.1 两个选择（明确回答）

① **恢复协调权＝跨进程排他**（不是仅进程内 mutex）。
② **暂停接纳范围＝同一实际物理输入资源 scope**，跨 turn、聊天 session、房间与 workspace。**不**无差别暂停全部聊天或所有 Windows 登录会话：纯文本生成、只读诊断、不使用该物理输入资源的操作**可以继续**；恢复涉及的旧运行及其自动重派发**另行冻结**。

`local_model_switch_drain_gate` **继续只管模型服务**，不复用成 CU 输入闸门（两设施不等价）。

### 2.2 签发者与证明对象

由宿主中组装的 **`InputSafetyCoordinator`** 负责：取得跨进程恢复排他 → 在共享资源状态中**关闭新输入接纳** → 取得**真实**旧执行者与运行关系证据 → 产生**有限作用域**的 `RecoveryControlGuard` → 驱动遗留运行收敛。

资格至少绑定：`resource_scope`、`recovery_operation_id`、`coordinator_instance_id`、`recovery_epoch`、`gate_revision`、来源数据库与候选运行集合、允许执行的恢复操作。

**恢复协调资格 ≠ 人工解除批准**：它允许执行恢复检查与已裁定的非成功收敛；需要原生人工确认的解除仍走**原生控制面**。

`new_input_intake_paused` **只能作为日志中的结果字段**，不得再作为调用者可任意赋值的事实依据；`recovery_control_authority` 的可序列化内容**也不能单独**代表持有实际排他权。**资格失效后不得继续修改安全状态**；重启读取旧恢复意图时**必须重新取得协调权**，不能反序列化旧 token 继续用。

### 2.3 锁与执行顺序

- 复用／扩展**当前输入 broker 的资源作用域**；**锁名不得包含** workspace、安装目录或调用方自选数据库路径（避免同一桌面因不同路径拿到两把互不相干的锁）。
- 用 Windows 命名 mutex 时，**持有与释放放在固定原生线程/受控平台层**，不让异步任务跨线程移动线程所有的锁；`WAIT_ABANDONED` **只表明**需核查受保护状态，**不是**资源已安全。
- 固定顺序 **R1–R9**：R1 取得同 scope 唯一恢复协调权（重复者返回忙或附着既有状态）→ R2 在共享库持久化恢复意图与关闭接纳（失败则不进入收敛）→ R3 撤销尚未激活的普通输入许可、登记已接纳/已派发的在途操作 → R4 请求相关旧执行者停止并核查真实身份（等待与收尾**均有界**）→ R5 为未确认风险建立**真实 incident**并取得**已验证**阻断引用 → R6 按实际关联核对旧运行 owner、提交候选、控制资格与当前 revision → R7 在来源会话库**同事务**提交 `Interrupted` 等已裁定终态及收敛事实 → R8 更新共享恢复操作的提交阶段（崩溃后按**同一 recovery ID** 对账）→ R9 **仅在独立资源安全条件成立时**重新开放新输入，否则保持隔离并**呈现恢复入口**。
- **"暂停新接纳"≠ 此前已派发的输入已经停止**：这两个检查**分别出具结果**。新许可签发与关闸必须处于同一协调顺序：关闸先发生则不得激活新动作；先前已激活者属在途，计入 R3/R4。
- 取消、必要释放与迟到事实写入**不能反过来等待**自己正被恢复协调器持有的锁；共享库事务保持**短小**，不跨模型请求、helper 等待或人工确认持有。等待人工时可释放恢复排他，但**持久化阻断不解除**；收到确认后**重新取权、核对 revision**再继续。

### 2.4 owner 解析与 Goal 锚点

- 只通过**确定的外键/记录关系**解析 owner。
- **没查到映射、查到多个候选、旧运行缺字段 ⇒ 均属"未知"**，不是"没有 owner"。
- Goal 运行可作其**真实执行锚点**，但**不能**把 Goal ID 填进 chat run／公开 turn 字段。
- **不要求**为补一个 `owner_id` 就改造全部历史运行；新操作可登记明确执行关联，历史**保持真实缺口**。
- 旧版本若不理解新闸门，**必须先受控停止该实例**；不能声称新 epoch 已经限制了它。

### 2.5 跨库失败保持可恢复

先建立**真实共享阻断**，再关闭历史运行；**关闭历史运行不自动关闭 incident**。跨库任一阶段失败，恢复意图要能解释已完成部分；**不能**用"回滚会话事务"为由把已建立的安全阻断随手删掉。**零输入且资源安全已独立证明**时可不建立不存在的释放事故，但此时应有**对应安全检查证据**，而不是"空 `resource_blocking_refs` + `resource_safe=true`"**自证**。

**RD4-02 的库、RD4-03 的协调器与最小原生恢复入口共同构成可发布单元**；代码可拆分开发，**未齐备前不能以 turn 级绕过维持正式自动输入**。

## 3. 构建与收据（PKG 侧）

### 3.1 §C-24：维持拒绝发布，允许"准备后重新冻结"

不设 `Cargo.lock`／`tauri.conf.json` 的构建中变更白名单。两阶段：
**准备阶段**：解析／更新依赖、生成必要配置 → 展示变化并按既有变更政策确认 → **冻结完整输入快照**。
**正式构建阶段**：只消费冻结输入 → 构建、测试、导出、打包 → **任一声明输入改变即拒绝发布**。

Cargo 正式入口用**锁定语义**：在既有离线要求下采用 `--locked --offline` 或等价 `--frozen`（`--locked` 在需要改锁文件时**失败**；`--frozen` 等价于锁定 + 离线）。生成式配置：能在准备阶段生成的，生成后**计入冻结输入**；需构建中产生的中间文件放**已声明的派生输出位置**并记录生成来源；**不能**发现被改写后把它从输入清单移除以换取绿色结果。诊断显著列出**实际改变的路径、前后摘要、发生阶段**与 `release_eligible=false`。

### 3.2 §C-26 / §C-27：**P0**，同一工单完成"发布权 + 代次绑定"

**批准 P0，但限定结论**：属**发布证据完整性缺陷/风险**，**不是**已证明签名或分发了错误包（尚未经验性构造出那一交错；现有消费侧拒绝仍是有效缓解，不得在升级优先级时抹掉）。

**最小修复不得停在"再核一次哈希 + 补字段"**：同一槽位发布权必须覆盖 **产物最终核对 ＋ 收据生成与提交 ＋ 当前有效代次的发布**；失败竞争者的 `catch/finally` **只能写自己的诊断**，不得向共享有效槽位发布自己的收据；**写前复核若不受同一排他保护，仍可能在复核后被替换**。

固定代次语义：`slot_key`（规范化实际输出槽位身份，同一位置的竞争者必须相同）／`generation`（一次成功发布的**不可变代次 ID**，**不用 mtime**；相同字节的两次发布也可有不同代次）／`producer_run_id`／`artifact_digest`／`receipt_digest`／`build_input_digest`／`consumer_run_id`。

消费端固定流程：取得读取资格后 → 读取**明确 generation** → 核对收据与产物 → 复制到本次打包的**独立 staging** → 核对复制内容 → 固定本次消费收据 → 释放共享槽位读取权 → **从本次固定收据生成报告**。**禁止**报告生成时重新读取共享槽位的"最新收据"。已消费 G1 后槽位合法更新到 G2，**G1 报告仍可有效**（依据是保存的 G1 收据与本次 staging，不要求指针永远停在 G1）。每个被正式包引用的代次收据须**可追溯保留**；失败运行**不得**出现在成功的 `exported_artifacts[]` 中。

**授权**：本轮明确授权修改 `package-all.ps1` 的 `exported_artifacts[]`，与 PKG-L07c 补强**同 PR 或连续绑定 PR**，由当前脚本负责人负责。

### 3.3 验收（7 项 + 真实双进程）

失败方不能覆盖赢家收据／产物提交与收据提交之间退出消费者拒绝不完整代次／消费 G1 后发布 G2 报告仍精确绑定 G1／generation 正确但内容错配仍拒绝／同一 generation 对应不同收据内容判冲突／失败报告不能被执行 `--no-build` 当作有效发布收据／**测试不仅断言字段存在，还要核对它与实际消费内容一致**。并发时序用**真实双进程 + 可控屏障**。

**P0 关闭前暂停受影响路径的正式发布晋升**；单发布者模式可用于诊断与修复验证，但**不能**仅凭"这次没开并发"绕过已知收据完整性问题。

## 4. 读取器所有权、统计与接纳顺序（一个工单联合实施）

### 4.1 §C-17（选②）：`Saturated` 不再丢掉仍存活的读取器

预留槽位**从 reader 创建前一直持有到实际回收**；`park_retained` 原则上**只是 `Active→Retained` 的状态转换**，不在收尾时重新竞争另一个容量池。正常路径的不变量：**预留未创建 ＋ 活动未回收 ＋ 已保留未回收 ≤ 8 个 reader 容量义务**。

若仍因契约破坏进入 `Saturated`：① 返回明确的**严重内部故障**；② **保留** reader、线程句柄、管道与缓冲区的**所有权**；③ **锁住该监督器的新 helper 接纳**；④ 有界取消／回收，未完成对象**仍受管理**；⑤ 记录**实际数量**（含已超出正常不变量的部分）；⑥ **不自动恢复**服务能力，直到对象回收与故障状态完成核查。

允许调整内部返回类型使失败结果**携带仍归调用方/监督器持有的资源**，但必须确保**生产调用者实际接住**——不能"返回一个带句柄的错误后立刻丢弃"。**不采用**无限增长的"应急 Vec"来假装资源有界。**仅凭文档不得宣称该分支绝对不可达**，应记为"正常接纳路径已前置预留，异常分支通过**故障注入**验证"。

### 4.2 §C-18：拆分"未回收"与"受持有"

**不能**简单写 `Saturated → holds_unreclaimed_reader() = false`（修复后若故障资源确实由监督器持有，返回 true 才是正确事实）。至少区分：

| 指标 | 定义 |
| --- | --- |
| `unreclaimed` | 已创建但尚未完成回收，**不代表**一定还在执行 |
| `owned_unreclaimed` | 未回收，且产品仍持有**可管理**的对象与句柄 |
| `unowned_unreclaimed` | 已知未回收，但当前**已失去**必要管理所有权 |
| `admission_rejected` | 容量不足等原因导致拒绝；**拒绝本身不代表创建了 reader** |
| `capacity_fault` | 实际状态违反正常容量或所有权契约 |

`readers_retained` 应反映**真实受持有数量**，不是把所有错误状态都计为 1。旧"分离但存活"场景记 **未回收且未受持有**；修复后的"故障但仍持有"记 **受持有且故障**。这些数值**不是**内存字节数或精确运行线程数，名称与 UI/诊断**不得混用**；按 **reader 唯一身份**聚合，避免错误回传与监督器汇总**重复计数**。

### 4.3 §C-21（选②）：预留前移到 `spawn` 之前，并保护安全收尾容量

顺序改为：校验请求与执行资格 → **计算普通 helper 与必要清理的最大 reader 需求** → **一次性预留容量** → 创建并监督 helper → 创建/绑定读取器 → 最终输入前检查 → 允许业务输入。

**必须防止收尾死角**：普通 helper 不能占满全部容量，导致需要独立释放时**没有读取器配额**。若独立释放 helper 使用同一读取机制，应在**普通动作接纳时**连同可能的一次清理所需容量**一起预留**（仍计入上限 8）；清理时**转用该预留**，不重新竞争普通容量，也**不递归**为清理再创建下一层清理额度；若清理机制确实不用该池，**按真实资源模型记录，不虚增需求**。

`spawn` 失败且未创建 reader ⇒ **归还全部未用额度**；部分创建成功 ⇒ **只归还未用额度**，已创建对象的额度直到真正回收才释放。**容量等待消耗原有预算，不能重置任务期限**。

**验收**：容量不足时 **helper spawn 次数为零**；两路 stdout/stderr 按**实际 reader 数**计量；中途失败**不泄漏或重复归还**；**饱和下已预留的必要释放仍能进入受控收尾**。

## 5. 命令行计量与环境例外

### 5.1 §C-16：接受软门槛，但**纠正计量口径**

批准保留 `<31_000`（不恢复 3KB 断言、不提高硬上限）。但**这不是"约 1.8KB"的容量保证**：Windows `CreateProcessW` 上限为**包含终止空字符在内**的 32,767 个**字符**，须按**实际 UTF-16 单元**核对完整命令行 = 程序名/必要引号 ＋ 所有参数及真实转义 ＋ 实际编码后的脚本参数 ＋ 终止符。

若 30,014 **不含终止符**，则硬限剩余 = `32_767 − (30_014 + 1) = 2_752` 个单元——**不得**写成 UTF-8 字节余量；`<31_000` 留下的是约 **1.77 千个该口径单元**的最低余量。

**还应测试**：最长受支持路径、空格／中文、参数转义及实际动态输入（**只测某个脚本常量长度不够**）。新增的两个测试接缝须**分别输出测试版与正式版长度**，并确认**接缝不能**通过正式 CU 参数、环境开关或用户设置启用。若 helper 将来继续增长并超过软门槛，应**缩减或重构**传输/脚本交付，**不再默认逐次放宽阈值**；本轮**不强制**引入预编译 helper。

### 5.2 §C-23／§C-22／§C-7：环境例外回到**测试污染治理**范围

"指定环境例外"原意＝**此前逐项登记的进程环境变量/cwd 测试隔离例外**，**不是**"环境不满足就跳过"。RD4-10 的目标就是这些点；对外部依赖的盘点与显式跳过**有价值但不能作为该工单已完成的替代证据**（逐项审查后保留有独立价值的部分，不盲目全量回退）。

| 情况 | 允许的结果 |
| --- | --- |
| 测试平台确实不适用 | 明确记录**未编译/不适用**，**不计运行通过** |
| 可选外部依赖缺失且前置有真实探测 | 可**明确跳过并独立统计** |
| 该能力属**当前发布必验范围** | 缺前置 ⇒ **验收未完成**，**不能用 skip 令发布门禁全绿** |
| 运行后发生断言失败／容量耗尽／超时 | 记录**失败**；**不能再改标**环境缺失 |
| 测试修改全局环境后没有恢复 | **必须修隔离**，不能用串行或跳过替代 |

**台账分两项**：① 测试外部依赖与跳过策略（附属测试治理）；② 环境变量/cwd 污染收口（RPR-01b／RD4-10 的**实际目标**）。

**RPR-01b 范围（确认立项/续办）**：tool-registry 中仍有问题的环境变量测试；core-runtime 中仍有问题的环境变量测试；所列 `#[cfg(unix)]` 的 `PATH`/`SAFEUSER` 污染路径；此前已授权的 command-router 新例外作为**单独子项**接入（不借此扩大到所有生产配置逻辑）。优先用**显式环境参数或 `Command::env`**；必须改进程级环境时，复用同进程**统一锁 + RAII**，并保存"缺失/空值/有值"的真实差别。**Unix 不能只加一把局部锁就宣称线程安全**（其他线程与依赖库可能直接读环境），这类测试**优先用隔离子进程**。**Windows 通过 ≠ Unix 已编译**；加 Unix target 的编译检查 **≠** Unix 运行测试；**Unix 子项在匹配环境编译并运行前保持未验证**；可先合并关闭已验证的 Windows 子项。**"永久污染"**应精确为"当前测试进程后续执行被污染"，**不代表用户系统环境被永久改写**。

## 10. 关闭与发布规则（裁决 §八）

状态四分：**已裁决 / 已实现 / 生产已接线 / 目标环境·安装已验收**。§C-1..§C-15 关闭"选择待定"，**不能**批量关闭实现。

**正式发布必须满足**：共享安全库有**真实生产者与消费者**（不只是一条解析路径）；恢复资格与暂停状态由**实际协调器**证明（不接受调用方自证）；遗留运行收敛、共享阻断与原生恢复之间**没有放行空窗**；收据、产物、消费代次与报告**可精确关联**；reader **正常容量与异常所有权都被验证**（不能靠丢句柄维持"表内 ≤8"）；未执行、目标不适用、依赖缺失与失败**分别报告**，不通过扩大 skip 获得全绿。

**回滚不得**：清空安全库、删除未决 incident、恢复按 turn 绕过的输入策略、把失败收据提升为有效产物。数据库、脚本与程序回退按各自兼容边界执行；**已发生的输入事实不随代码回滚消失**。
