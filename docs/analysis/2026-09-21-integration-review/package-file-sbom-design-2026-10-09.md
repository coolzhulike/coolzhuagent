# 文件级 SBOM 补充导出方案

本项承接工作包6.4的交付可追溯性，先完成真实交付文件的标准清单，完整库依赖、许可证和签名仍开放。不新增运行时服务、数据库、前端调试信息或发布阻断门，也不改已经冻结的0.2.125四个发布资产。

## 事实边界与职责

`scripts/export-package-sbom.ps1`消费已有`package-report.json`与`payload-inventory.json`，复用`scripts/lib/build-identity.ps1`的JSON解析、报告规范哈希及载荷规范哈希。先校验报告内容身份、清单引用、三种构建身份、路径唯一性、文件数、总长度和载荷摘要，再导出CycloneDX 1.6 JSON。版本、target、源码提交取冻结报告，不取当前工作树。

应用组件包含实际清单中的文件组件，每个文件只声明相对路径、实际长度和SHA-256；载荷集合摘要属于构建属性，不冒充MSI或任何单文件哈希。不导出环境凭据或用户配置路径。清单自引用载体`payload-inventory.json`依照原口径排除，其实际文件SHA作为来源属性登记。

输出的组成完整性明确为`incomplete`。不把文件包含关系伪装成库依赖图，不把工作区Cargo.lock内未编译的可选依赖、开发依赖或宿主构建依赖冒称运行时库。报告自校验只证明字节及关联一致，不证明作者、来源签名或跨机器逐字节可重现构建。

## 风险审查与取舍

- [CycloneDX官方规范](https://cyclonedx.org/specification/overview/)区分组件、依赖图和组成完整性，因此本次只声明文件包含关系并保留不完整标记。
- [Cargo官方说明](https://doc.rust-lang.org/cargo/commands/cargo-tree.html)说明依赖树不能保证精确等同实际编译结果；现有打包流程包含九个独立构建入口及一个独立Tauri工作区。完整库级SBOM应后续消费各入口实际编译收据，不能靠单次`cargo tree`拼出貌似完整的结果。
- 输入一次读取，字节哈希与解析对象来自同一份缓冲区，避免重读期间身份漂移。所有检查先于输出，采用同目录临时文件和不覆盖的移动；无效输入不得留下“通过”的SBOM。
- 新增脚本与原打包流程解耦，先对正式125归档报告做补充导出和官方Schema校验；下一批正常打包可调用该脚本。此次不改MSI内冻结源码、不修改原四资产数量。
- timestamp及UUID反映本次导出，重复导出不声称逐字节一致；文件路径/长度/SHA与冻结清单必须逐项一致。

## 验收

使用正式125的1159文件冻结清单，按官方JSON Schema做离线校验；独立逐文件比对Program Files实际安装字节。对自有输入副本修改一处文件摘要，验证导出失败且没有输出。保留原报告、来源摘要、执行日志、Schema来源及实操截图；不重测模型简单对话。

完整库依赖、许可证、漏洞/签名与发布索引的自动关联不纳入本次通过范围，6.4保持部分完成。
