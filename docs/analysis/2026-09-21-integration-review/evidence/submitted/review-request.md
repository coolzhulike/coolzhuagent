## 请优先回答的架构问题

比较三条路线并明确推荐及否决条件：A 保留 Rust/Tauri/SQLite，抽取共享运行时，吸收 DSH 契约与经过试点的组件；B 采用 DSH/Node 主运行时，Rust 成为 Windows 能力宿主；C 有明确边界的双宿主过渡。不要以包数量判断成熟度，不要引入两个会话事实权威或两个有副作用的同轮主循环。

请挑战下列初步建议：

- SQLite 仍为单一事务权威，事件表/outbox 与业务提交同事务；JSONL/SQLite 是物理介质而非是否能回放的决定因素。先固定 turn/step/request/tool 等身份、终态和事件契约，再分段抽出 Web 主循环。不要直接把 Web 切到功能不同的 CLI 循环。
- 同轮只有一个执行所有者；影子模式只比对决策/投影，绝不能执行真实键鼠或重复文件写入。
- 第三方插件/MCP/脚本先建立实际执行权限闸门、生命周期与取消契约，再扩张插件数量；不要把进程外或 VM 等同于安全沙箱。
- 统一参数页已有实现，应补能力探测、显式覆盖、参数映射、配置来源解释和秘密引用；不重做 Provider 表。
- UI 先独立资源构建/模块和槽位边界，再决定是否 React；保留现有产品视觉和用户数据。
