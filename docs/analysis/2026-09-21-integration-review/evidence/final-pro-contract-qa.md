# 6 Pro 返回计划的最终契约交叉检查

日期：2026-09-21。范围：只读检查 `gpt6-pro-review-original.txt`、`implementation-contracts.md`、`contract-qa-resolutions.md`、`execution-detail-supplement.md`，并定点读取定时任务授权源码。本文没有修改产品、04/05/06，没有执行真实模型、Paint、打包或安装测试。

结论：总体方向可执行；以下五项应在最终计划中明确覆盖候选材料。后三份文件是本地实施细化，不是 6 Pro 原文。Pro 的人日、样本和预算都是建议值。

## 1. 发送、路径点数与释放需要补完整的字段约束

**现存矛盾**：`contract-qa-resolutions.md` 的“`confirmed_point_count` 的 0 只能在确认零输入时填写”与“点数只统计路径采样，不把 down/up 当路径点”不能同时成立。确认 down 已发出、首个路径采样点前停止时，`input_delivery=sent` 与路径点数 0 可以同时为真。此外，本地候选正文尚未完整定义独立释放维度，而 Pro 已要求它。

**精确修订**：

- `input_delivery` 固定为 `not_sent / may_have_been_sent / sent`。至少一个输入事件得到可靠发送确认即为 `sent`；已知部分执行不得降格为“完全未知是否输入”。
- `partial` 为布尔或 null：已知只完成动作的一部分为 true，已知无部分执行为 false，无法判断为 null。非路径动作也可发生部分输入，但必须按该动作的输入事件定义判断。
- `confirmed_point_count` 仅统计声明过采样口径的路径点；非路径动作设 null。0 表示“确认没有已完成的路径采样点”，不表示“确认没有 down/up/按键输入”。如需要总输入确认数，另用定义清楚的 `confirmed_input_event_count`，不得混用两个分母。
- `path_completed` 仅对路径动作适用，非路径动作设 null；true 表示全部目标路径点已有发送确认，不证明释放或应用效果。路径尚未开始但 down 已发出的合法例：`sent + partial=true + path_completed=false + confirmed_point_count=0`。
- 动作收尾记录独立 `release_status=not_needed / released / unknown`：仅在确认无本动作产生的释放义务时填 not_needed；释放回执可靠时填 released；无法确认则 unknown。运行中的尚未收尾可用 null，不能把它写成最终 not_needed；最终记录不得遗漏释放字段。动作若没有输入但承接到未知的旧 owner 残留，桌面整体仍不得因此视为已释放。
- 释放仅处理本执行器可靠追踪的自有按下状态；检测到用户已按下的修饰键不能无条件替用户抬起，应停止/等待并重新观察。

**补测**：down 后、首路径点前故障；已确认部分点后失联；完整路径后 release 回执丢失；非路径 click 的 down 已发/up 未知；迟到 release 回执。都独立检查发送、点数、路径、释放、目标验收，不能用一个字段推导其他字段。

## 2. “只更新同一条动作”与终态不可倒退，要允许迟到事实追加

**缺口**：`implementation-contracts.md` 写“后续只更新这一条状态”，迁移细则写“不生成第二个终态”，但若按字面把终态后的更新全拒绝，会吞掉取消之后迟到的真实输入、释放和 usage。Pro AR-09 已指出这一点；还需明确其与 authority epoch/outbox 的关系。

**精确修订**：

> action_id 标识一个动作，不重复执行；它的当前状态是投影。输入、释放、截图和 usage 回执按各自稳定回执身份追加事实，重复回执幂等消费。运行控制终态通过单写者的条件更新只决定一次；取消/超时后迟到事实可更新审计和统计，不重新打开运行，不发新动作，也不把任务改写为成功。取消请求收到、停止接纳、执行器停止、释放确认分别记录。

> 同一业务提交中的状态变化、对应事实和 outbox 在同一 SQLite 事务提交。outbox 重发只能重发事件，不能触发副作用重放。初期旧业务表仍是指定字段的权威；按会话停写、无活动 run、完成基线核验后，才可选择切换 authority epoch。新旧写入口须比较当前权威模式与 epoch，旧 owner 不得继续提交业务状态。旧 epoch 的合法迟到回执经独立对账入口验证动作身份后可记录原始事实，不复活旧 owner，也不借回执改写新 epoch 的控制状态。

**补测**：取消已落库后输入/usage/release 回执才到；重复回执；提交后广播前崩溃；权威切换后的旧 writer；旧 epoch 的有效迟到事实与伪造/错房间回执。迟到已知 usage 计一次，控制终态保持原值。

## 3. UIA 超时后，“没观察到效果”不足以允许物理补点

**缺口**：候选写“语义不可用才用受控物理输入，禁止两个后端都执行一次”；Pro 也禁止 UIA 超时后盲补。但实施人员仍可能把超时后截图无变化解释成“不可用”。UIA 请求可能尚在进行，随后才生效。

**精确修订**：

> 仅在语义操作尚未发起，或已确认前操作不会再执行且确认没有产生效果时，才允许选择物理后端。调用已发出而超时/失联时记录结果未知；停止后续输入，先终止或确认旧操作结束、确认释放与当前状态。仅凭一张无变化截图不能证明无副作用或没有迟到执行。恢复使用新动作身份，绑定原动作关系与共享剩余预算，不通过换 ID 绕过预算。

**补测**：UIA 超时后延迟成功、UIA 返回失败但应用状态已变化、语义不支持且根本未调用、旧请求无法结束。前三者分别验证不补点、保留事实、允许受控后端选择；无法结束时保持隔离。

## 4. 样本数、用量和性能阈值不能成为本轮已授权或已验收承诺

**歧义位置**：Pro 4.5 写“建议第一轮只批准 10 个配对短任务”、300 万输入/20 万输出，L1 每类 30 次至少 27 次、L2 30 次至少 24 次。若原样作为 04 的执行命令，容易误读为本轮已获该额度或已冻结验收标准。其 `≤1px`、误拒率 `≤5%`、P95 释放 `≤1秒` 也处于不同的测量口径。

**精确修订**：

> 本轮交付为审查和计划，未因此新增执行真实模型/桌面实验，也未消耗或确认这些预算。Pro 的 10 配对/20 run、300 万输入/20 万输出计量阈值及确认阶段 30 次/30 对均为候选。具体工作包开始前预注册每项分母、任务类型、设备、模型/参数、独立评分标准、停止条件、可承受用量与缺失 usage 的处理；使用既有用户授权时也必须符合其任务范围，不能把 Pro 文本当作新的授权。

> 计量阈值不是账单上限；正在执行的请求可能超出阈值，缺失 usage 使总消费无法由已知值保证。候选实验在启动请求前依据可用预算/最大输出做准入，记录在途量和未知量；到阈值停止新请求并保留事实。确认试验另定预算。坐标宿主变换误差与模型选点误差分别统计；任何有限样本的零违例均只陈述该样本，不能宣称总体故障率为零。

**补测/记录要求**：计划中保留这些数值的“建议、待预注册”标签；06 的未执行状态不变。把确定性的权限、身份、无盲重放与诚实终态作为相应固定测试集内的必须通过项，不以放宽这些不变量换取通过率。

## 5. 定时任务临时 full-access 已由源码核实，但需准确限定作用域

**静态事实成立**：当前快照 `modules/gui-web/packages/web-console/src/main.rs`：

- 2276–2295：`SessionGrantRecord` 储存在进程内 `OnceLock<Mutex<BTreeMap<...>>>`；key 由 workspace/session/tool 组成，不含 room/run/job。
- 2317–2325：会话 `*` 且 `full_access=true` 的 grant 可作为该会话的工具授权。
- 2385–2406：授权记录插入共享表，带 TTL。
- 8522–8546：普通 `deliver_scheduled_task` 若 task.permissions 包含 `full-access` 且同 key 无记录，向目标会话写入 `*` grant，TTL 300 秒。
- 8548–8564：随后等待 `api_chat_send`，正常返回路径按同 key 删除本次认为临时创建的 grant。

本次读取文件 SHA-256：`0a2d2a41c1d24113ae83a27842d25e3b20bf1298b4492a5ee67a7ac6aedcdf15`。这证明**共享会话级内存授权**行为，不证明持久 `coolzhu.toml`/聊天室权限字段被修改，也不是对所有会话的系统级全局提权。未跑并发或 future-drop 故障，不能把并发借权、误删用户新授权或异常遗留写成已复现事故；目前仅是由 key/生命周期推导的待测风险。本次只核实普通消息型定时任务，未把结论泛化到全部 Goal 定时分支。

**精确修订**：

> 将普通定时任务执行期间的共享会话 `*` 临时授权，改为唯一 grant_id 标识且绑定 workspace/session/room/job/run、能力范围和失效条件的执行授权。任务在执行入口持有自己的授权引用；清理只撤销该 grant_id，不删除用户授权或并发任务授权。用户既有 FullAccess 及 debug 默认语义保持兼容。任务取消、异常退出、重启恢复和 TTL 到期都必须通过统一授权解析器使后续动作失效；恢复任务不因历史授权存在就自动重新执行。

**补测**：同 session 不同 run 并发；两个临时任务交错结束；任务期间用户新授予/撤销；future 取消、重启、TTL 到期；存在已过期旧 key。检查其他 run 不继承临时能力、用户授权不被清理误删、任务不通过恢复绕过当前权限。
