一、审查结论

明确推荐路线 A：保留 Rust / Tauri / SQLite / 现有 Windows 发布链，从已发布 Web 产品路径提取共享运行时，吸收 DSH 的契约、生命周期与测试机制；不把 DSH 改成当前主运行时，也不默认引入双 Agent 宿主。

Paint 剩余失败仍有值得实施的 Agent 侧方案，而且其中一部分不是“优化模型表现”，而是必须先补齐的可靠性契约。 但现有材料不足以证明这些改动一定能让 qwen3.8-flash 完成海绵宝宝绘制，也不足以把剩余失败全部归为 Agent 缺陷。正确路径是先把输入事实、观察失配、工具状态、反馈和恢复链做成可审计闭环，再进行同条件实验。

1.2 必须锁住的四条边界

第一，DSH 与 ZCode 是两个不同对照对象。 DSH 提供的 Computer Use 基础包是独占 provider 注册服务，实际 provider 位于实验包；这不构成 ZCode 的实现证据。ZCode 随包技能能支持“它向模型公布了哪些接口与规则”，不能支持“Windows Paint 已经成功”。

第二，1175 项通过不是 Paint 通过。 这是 0.2.14 历史发布的自动化结果，另有一项 Anthropic 在线测试跳过；Paint 目标未通过必须继续单列。

第三，R1–R6 不是同一版本、同一初态的六次独立重复实验。 它们横跨多次修复，R5 还沿用了错误的工具选中前提，因此不能计算“0.2.14 Paint 成功率为 0/6”，更不能用于 coolzhu 与 ZCode 的成功率排名。

第四，本轮重构必须保留现有产品资产。 统一参数页、百炼 Base URL、已有密钥、图片直传与默认视觉转述、当前聊天布局、工具状态、搜索与统计、玉石控件和竹林背景，都应进入回归基线，而不是作为重写后再补的功能。

三、三条路线的裁决与否决条件

3.1 路线比较

路线本次裁决主要理由否决或重新评审条件
A：Rust/Tauri/SQLite 渐进整合推荐，作为正式主线保留现有数据、Windows 能力、Goal DAG、记忆、浏览器桥、ClawBot、语音、桌宠和 UI；最紧迫问题集中在边界、事实模型和执行契约，不要求更换语言或物理存储。若实际提取试点连续不能满足单所有者和行为兼容，而 B 已通过同一套完整验收；或新增明确需求要求大量 Cordis 原生服务，且经原型测量确认桥接总成本高于迁移成本，则重开路线决策。不能仅因文件大或进度慢自动转 B。
B：DSH/Node 主运行时，Rust 能力宿主当前否决，不列入主线实施尚无同条件产品验证，也没有现有数据、权限、图片、Goal、记忆和 UI 的完整迁移方案。DSH 的测试和服务化机制值得参考，但包数量不能抵消迁移风险。只有锁定可追溯源码、完成依赖审查、通过现有功能黄金集、证明可恢复迁移，并实现 Rust 能力的取消/权限/副作用回执后，才允许重评。
C：有边界双宿主保留为后续受限试点，不默认发布可以验证某个 DSH 子 Agent 或服务的价值，但会增加双进程状态、取消、凭据、预算和恢复成本。同一 session 双写、同轮两个副作用循环、共享未隔离工作区、不能硬停止子进程、不能解释未知效果、不能完整卸载，任一出现即否决。

路线 A 允许受监督的 Node 工具工作进程，但前提是它不是第二个会话主循环，不拥有 coolzhu 会话权威，也不自行派生长期自治任务。

若以后引入完整 DSH Agent，即使从 ACP 启动，也应明确登记为路线 C 试点，而不是把双宿主隐藏在“工具适配器”这个名称下面。

附件支持保留 A 独有资产和从当前 Web 路径提取，而不是直接切换到现有 CLI 的非增量 ConversationRuntime。

3.2 所有路线共同的硬否决条件

无论采用哪条路线，以下情况都不得进入发布：

  1. 一个会话存在两个独立事实写者，或同一调用被两个执行循环实际执行。

  2. 为提高 Paint 成功率关闭窗口身份、DPI、目标有效性、取消释放或权限检查。

  3. 未知副作用被自动重放，或“工具已返回”被显示成“用户目标已完成”。

  4. 静默修改 Base URL、凭据来源、图片路由、发布默认权限或现有聊天布局。

  5. 新数据库只能升级不能安全打开，且没有经过演练的停机备份与恢复路径。

4.3 03 尚未充分覆盖的三个待验证风险

第一，语义幂等键与新尝试可能混淆。 现有监督器按目标、约束等生成任务键，并缓存终态。需要测试：同一轮中，外部状态已修正后，合法的新恢复尝试是否仍命中旧失败缓存；反过来，是否能靠换 ID 绕过预算。此处只是风险，不是已确认阻断原因。建议区分网络重复提交、同一动作重传、参数纠错、显式恢复四种身份。

第二，Windows 输入环境不能只检查坐标。 SendInput 受完整性级别限制，也不会自动清除已有按键状态；失败返回不能完整诊断 UIPI 阻断。因此应补测目标应用完整性级别、用户残留修饰键和焦点变化，但不能为绕过失败而自动提权。这里依据的是 Windows 官方接口约束，不是附件中的已复现 Paint 缺陷。Microsoft Learn

第三，租约不能约束任意外部程序。 产品输入 broker 可以约束自身所有正式输入路径，却不能宣称阻止用户、其他应用，或显式完全访问下任意程序操作桌面。因此手动干预检测、观察失效和停止机制仍然必要。

4.4 保留 task-level 严格 JSON 控制器，但补齐状态闭环

不建议为模拟 ZCode 的 Node REPL 形态而替换现有 CU 控制器。

ZCode 随包契约声明了 AppRef、语义动作、截图光栅坐标、观察差分、短批次、actionSent 和独占控制。这些适合作为接口设计参照，但并不证明其内部用了某种 hash 放宽策略、具备多点画笔路径，或已经通过 Paint。

建议将 coolzhu 的受控闭环改成：

绑定应用与窗口 → 获取输入所有权 → 记录任务基线 → 观察并确认前置状态 → 规划一个动作或受限片段 → 宿主重新校验 → 输入 → 确认释放 → 有界稳定观察 → 判断动作效果 → 更新子目标 → 必要时最终视觉验收。

其中有六项关键设计。

A. 输入事实必须拆成四个正交维度

维度建议状态不允许的推断
输入发送事实not_sent / partial / sent / unknownsent 不等于应用生效；回执丢失不等于 not_sent。
应用效果unobserved / unchanged / changed / unknownhash 变化、鼠标移动、工具栏 hover 不自动算目标进展。
目标验收not_met / met / unknown选中矩形工具不等于已画出矩形，更不等于海绵宝宝完成。
输入释放not_needed / released / unknownhelper 退出不自动等于所有按键已释放。

对外需要三态兼容时，将 partial / unknown 映射为 may_have_been_sent，但内部不能丢掉已知部分输入与完全未知之间的差异。

恢复规则：

  • not_sent：允许在新观察、新动作身份和剩余预算下重新规划。

  • partial / unknown：先观察、确认释放和实际效果，禁止自动重放原非幂等动作。

  • sent 但后截图失败：保留已发送事实，任务验收为未知，不重复执行来“补结果”。

  • 释放未知：停止后续输入、隔离该 run，明确显示人工处置提示。

B. 首先做 frame 契约，再做语义 ROI

优先顺序应是 frame_id + 宿主坐标变换 在前，语义画布 ROI 在后。

建议 FrameRef 至少包含：

frame_id、图像变体 ID、返回光栅宽高、物理捕获矩形、裁剪/缩放/填充变换、窗口身份、DPI、观察代际、采集时间。

模型只输出它实际收到的那张图内的整数坐标。宿主负责：

  1. 检查 frame 是否属于当前 run、窗口和有效观察。

  2. 检查光栅边界。

  3. 按记录的变换映射到物理像素。

  4. 检查物理目标和允许操作区域。

  5. 在输入前重新验证窗口与目标。

旧的 0–1 相对坐标可以保留为版本化兼容入口，但不能与新光栅坐标自动猜测混用。

ROI 不能靠“最大的白色矩形”直接获得执行授权。 候选 ROI 必须有来源、frame 绑定和不确定性；绘图动作应要求语义绘图区成立。当前包含工具栏的客户区应明确命名为“交互范围”，而不是可信画布。附件已经明确该 fallback 包含工具栏。

C. stale 分层，而不是调大“有效期”

建议记录以下失配原因：

window_identity_changed、process_incarnation_changed、geometry_changed、dpi_changed、target_changed、raster_changed、generation_consumed、occluded、user_intervened。

当前实现未必已经区分这些原因；它们是新增诊断词汇。

处理应分两层：

  • 硬条件失配：身份、窗口几何、DPI、所有权、目标有效性或遮挡改变，拒绝旧动作。允许重新观察，但不是重新使用旧坐标。

  • 内容变化待解释：同一窗口内的图像变化，需要判断是否影响动作前置条件。非目标区域变化也可能是模态框、菜单或工具状态变化，不能简单“ROI 外一律忽略”。

输入前的验证性截图应与“发布给模型的新观察代际”区分。否则可能发生“为了检查旧计划而生成新代际，再因新代际拒绝旧计划”的自我失效。这只是必须测试的设计风险，不是对当前源码已发生该问题的断言。

D. 规划反馈必须有界、结构化

下一步 planner 至少接收：

  • 上一步动作及目标。

  • 输入发送状态、释放状态和错误类别。

  • 上一步验收结果与证据引用。

  • 已完成与未完成子目标。

  • 当前工具、颜色、焦点、弹窗等已确认状态。

  • 不得重试的原因。

  • 剩余动作、规划、恢复、时间预算。

建议新增反馈预算先限制在约 2K token 内，超限保留状态和引用，不截断 JSON、不灌入原始内部思考。该预算是实验起点，不是已验证的最优值。

E. UIA 语义动作要有“不能重复执行”的退路

先提供 selected / toggle / focused / supported_patterns，然后按实际支持情况增加 Invoke、Value、SelectionItem、Toggle。

物理输入回退只允许两种情况：

  • 执行前已知语义动作不受支持；

  • 执行后重新观察，足以确认前一次没有产生效果，并通过恢复政策批准。

不能出现“UIA 调用超时 → 立即补一次物理点击”的盲重试。Paint 是否提供所需 pattern，要按具体版本实测。

F. 短批次与降本最后做，且不省掉关键状态验证

首期不批量执行“选画笔、选颜色、拖拽”而只在末尾截图。可以先减少模型往返，让宿主在两个动作之间做轻量状态确认，但每个动作仍有独立校验、事实记录和取消点。

双层重复检测也应明确区分：

  • 执行重复：同一 action_id 不得再次注入。

  • 语义无进展重复：新 frame 上重复同一意图而目标状态不变，应触发停止或改计划。

不能直接去掉 generation 后，把合法的连续画笔操作全部判为重复。

4.5 Paint 实验设计与量化门槛

先分三层验收，不以低层通过代替高层

层级任务建议门槛
L0：输入与映射受控靶场点击、按下/移动/释放、坐标变换、取消、故障注入固定测试集全部满足事实与安全不变量；坐标变换误差在可控环境内 ≤1 物理像素。这里不评价模型选点。
L1：Paint 基本闭环干净画布；选工具并确认；画短线；画矩形；确认画布实际改变正式确认阶段每类 30 次，至少 27 次真实完成；样本内 0 次越权输入、0 次未知副作用自动重放、0 次假成功。失败逐次分类。
L2：海绵宝宝目标同模型、同参数、同 Paint 版本和初态；通过真实 UI 输入产生新图预先冻结低但明确的可识别标准和人工评分样例；建议实验门槛 30 次中至少 24 次达标，且样本内假成功为 0。未过只能标复杂绘图实验性，不能用 L1 通过替代。

L2 标准应允许画得粗糙，但至少要求本轮新增、可识别的目标主体与关键面部/肢体特征；具体评分样例应在实验前固定，不能看到结果后降标。程序生成图片、导入预制图、预录目标路径均不算这项 UI 绘画实验通过。

不要在真实桌面上重跑已知不安全旧实现作为 A 组。 两组先共享输入事实、独占、权限和取消安全底座，再比较策略变量。原始 0.2.14 及 R1–R6 可作为离线证据基线。

十次规划或十次任务只能发现明显问题，不能支持稳定成功率结论。确认阶段应报告分母和置信区间。即便 200 个反例全部没有假成功，也只能说明“该样本内为零”；它不证明总体假成功概率为零。

预算安排

保留默认任务 120 秒、12 动作等现有约束作为第一轮对照条件；在观察、规划、验收和输入前都检查同一个 deadline。收尾释放可有单独、明确的短宽限，但 deadline 之后不得启动新的业务动作。

建议第一轮只批准 10 个配对短任务，即 20 个 run，聚合已报告用量上限先设为 300 万输入 / 20 万输出 token；达到上限停止分析。只有出现收益信号才扩展至 30 对确认，另设预算。缺失 usage 的请求必须记录为未知，不能据此保证实际账单不超过这些计量阈值。

附件中 R3–R6 合计 457474 输入、14087 输出、29 个有 usage 的响应；其中 CU 内部已记录响应为 22 次。R4 验收输入约占 CU 内部输入的 51.1%，说明验收频率值得测量，但输入占比不等于金额占比，也不证明删除验收能同等降本。

五、原文 12 个架构决策的正式回应

决策结论执行要求
1. 权威状态模型采纳，但收紧定义。 保留 SQLite；先单写者，再追加事件和 outbox。初期旧业务表仍是对应对象权威，事件不能冒充完整历史。达到切换门禁后，运行/会话域可采用“基线＋事件”的逻辑权威，旧表转投影。每个对象在任一时刻只有一个权威模式。
2. 扩展机制采用双层扩展，不采用双主运行时。首方受审 Rust 服务在进程内；第三方工具/脚本/MCP 在受控进程外。manifest 只是声明，最终权限由宿主执行闸门决定。Cordis 模块不直接等价为 Rust 插件。
3. 前端形态采用原生 JS 模块化、注册表和独立构建。React 延后。先拆资源和面板所有权，保持现有布局；不移植 55 个客户端包，不恢复旧 Provider 页或可见三栏。
4. 权限模型映射修改为兼容解析层，而非枚举一对一重命名。分离允许效果、审批政策、沙箱能力和 room/caller 授权。debug/release 分开测试。FullAccess 当前先于 Protected 的行为先保持；改变它必须另作显式安全变更。
5. 进程沙箱范围采用，但先限 Windows 工具与脚本路径。shell、第三方插件、MCP、未来 PTC 逐步纳入。confinement 不可用时拒绝要求隔离的执行；GUI 输入 broker 作为单独高风险能力治理，不能宣称文件沙箱隔离了 Paint 的外部效果。
6. 配置归一层保留 coolzhu.toml 与现有参数页，增加显式 resolve。解析结果携带来源和 revision。会话覆盖暂不搬家，运行事件保存当次已解析快照，不成为第二套设置权威。配置写入增加版本冲突检测。
7. 迁移机制采纳相邻迁移、静态目录、前向版本拒绝。数据库、事件、wire、投影和旧 JSON 分别管理版本；迁移号由单一负责人分配，不凭报告直接占用“v21”。
8. 编排范式保留 Goal DAG；脚本 workflow 延后。DAG 继续拥有阶段与人工验收状态；统一并发、深度、预算、取消和 owner。workflow 后续只能作为某阶段的受控执行方式，不能再拥有第二套 Goal 状态。
9. 记忆归属保留 beads，增加来源和证据治理。压缩摘要默认是上下文维护产物，不自动等价于长期验证知识。记忆变更可审计；真实嵌入与词袋哈希分别标识。
10. MCP 归一保留现有 transport 能力，经适配统一生命周期。两侧前缀均为 mcp__<server>__<tool>；处理规范化、长度、碰撞和历史 alias，不做无意义前缀迁移。保留 OAuth 功能，迁移秘密存储；资源工具按需补齐。
11. 工具暴露与 PTC保留三档暴露；PTC 延后、默认关闭。可见工具集合绑定 registry/config/permission revision；执行时再次授权。未来先受控 Node PTC，不引入无文件沙箱的实验 Python 路径。工具暴露不是安全边界。
12. CLI/SDK/自动化入口统一异步运行服务，保留 HTTP/SSE；ACP 后置。先迁 Web 流式/非流式，再 CLI 与子 Agent。SDK 不能依据名称假定支持取消、审批和单次结果；ACP 也不承担全部 UI 呈现数据。

这些决定对应原文第九部分，但没有采纳“为了统一必须同时换存储、语言、UI 与所有 SDK”的隐含前提。

5.1 权限映射补充

权限映射必须按实际决策真值表验收：

  • Prompt 主要表达审批要求，不应直接映射成某种文件可写范围。

  • Allow 的旧调用语义需要确认，不能按名称迁成全权。

  • WorkspaceAuto / OutsideApproval 应保留原执行规则，再逐项迁入新 resolver。

  • FullAccess 保留已存在的兼容语义，但仍不能绕过 room 的 CU 能力要求、身份校验和取消。

  • 未知/动态工具缺少最低权限元数据时，返回明确配置错误，不默认 ReadOnly。

  • 定时任务不再通过修改会话全局权限实现临时提权；改为绑定到该次任务、范围受限、到期失效的授权。

附件确认了 FullAccess 与 Protected 的现有顺序、debug/release 差异，以及定时任务临时 full-access 行为；这些都是需要显式迁移的行为，不是可随手“统一”的名称。

6.3 SQLite 迁移：分三步，不直接全库事件溯源

步骤一：集中现有写路径。

由一个 SessionStore 实现承接现有业务写入。保留当前关系表语义，在同一事务内追加必要事实和 outbox。这个阶段的事件尚不完整，不能声称可还原所有历史业务状态。

步骤二：仅对运行/会话域建立可重建基线。

对停写、无活动 run 的会话建立基线，包含经过验证的消息投影、已有运行状态和来源标记。缺失的历史 tool/action 对应关系标为未知，不能根据时间相近猜造关联。

步骤三：按会话权威 epoch 切换。

达到一致性门禁后，明确将该会话切到“基线＋事件”逻辑权威；旧消息表等变为投影，旧写入口拒绝继续独立修改。未切换会话仍走旧权威模式。

Goal、beads、ClawBot 等领域可以继续保留各自关系状态，不要求第一期全部事件溯源；但写者、跨域事务和审计关系必须明确。

9.3 如何逐步缩小 main.rs

按“纯函数 → 有状态服务 → 外部执行 → 运行循环 → 路由适配”的顺序提取：

  1. 先迁请求解析、历史投影、参数归一和 usage 计算，保持输入输出完全一致。

  2. 再迁工具调度、审批和存储事务；原函数变成薄转发。

  3. 再迁异步 TurnRunner，Web 只保留 SSE/HTTP 适配。

  4. CLI 与子 Agent 接同一服务后，才能废弃旧循环。

  5. 每次删除旧代码都必须有调用图和回放证明，不以“减少多少行”为验收目标。

影子模式只能比较解析、计划、投影和请求快照。 不允许影子模型再次请求真实云服务后自主调用工具，更不允许重复文件写入或键鼠输入。

十一、发布、回滚与未解决风险

11.1 发布门槛分两级

基础整合版本允许发布的条件：

  • 现有模型参数、图片路线、聊天体验和数据兼容没有退化。

  • 动态工具权限、输入所有权、取消、未知副作用和真实终态门禁通过。

  • 有安装版、真实原生窗口、升级和恢复证据。

  • Paint 只对已经验收的能力作声明。L1 通过而 L2 未通过时，明确标注“复杂绘图仍属实验性”。

只有 L2 通过预先冻结的真实实验标准，才允许宣传对应配置下的海绵宝宝任务通过。 不能因为复杂绘图未过而阻塞所有架构改善，也不能把它藏进整体通过统计。

11.2 备份和回滚策略

备份不是直接复制一个正在写的 .sqlite3 文件。 采用一致性备份机制，或排空所有 writer 后备份；同时记录配置 revision、附件引用、秘密存储恢复信息和安装包版本。

建议发布前保存成套恢复点：

  • 数据库及一致性校验结果。

  • coolzhu.toml 与配置 revision。

  • 附件与被审计引用的证据对象。

  • 受保护的凭据备份/恢复说明。

  • 当前二进制、资源 manifest、源码身份和文件哈希。

回滚分三类：

情况处理
只读 UI/索引/性能策略失败回退视图或策略；索引重建；权威事件和数据不回退。
新服务失败但 schema 仍兼容停止新会话接纳，排空活动 run，切回已验证 adapter；统一安全门禁必须保留。
权威模式或 schema 已不兼容停写后恢复匹配的成套备份；迁移后的新写入先隔离保存，不得静默丢弃。禁止让 0.2.14 旧 writer 直接操作新库。

GUI 取消和程序回滚不能撤销已经发生的鼠标操作、文本输入或外部发送。自动 Ctrl+Z 也不应被当成通用恢复，因为它可能撤销用户后续操作。

11.3 仍然未解决、必须公开保留的风险

  1. 源码身份与完整调用链尚未由本轮复核。 第一阶段必须验证审计中的定位和动态权限、输入锁等可达性。

  2. Paint 的具体 UIA 能力、stale 子原因与部分输入风险尚无完整实验。 新接口不能代替真实 helper 与 Paint 验收。

  3. 模型自身可能仍无法在既定时间/动作预算内完成目标。 通过前置状态和反馈改进后，仍需单独评估空间规划和绘画表现。

  4. Windows 桌面是共享外部状态。 租约不等于 OS 级独占，更不等于能阻止用户和其他程序。

  5. DSH 的本地 MIT 声明与包清单不构成依赖许可或运行安全审查。 当前快照也不能被称作已确认最新版。

  6. ZCode 文档不能用于反推私有实现。 后续若无法使用同一模型与参数，只能开展产品端到端对照，不能称为纯运行时优劣的控制变量实验。

最终裁决

这次整合的主线不应是“把 coolzhu 改造成 DSH”，而应是：

让系统知道自己刚才做了什么、是否真的输入、现在选中了什么、观察为什么失效、哪些效果不能重放，以及凭什么声称任务完成。

这些能力补齐并通过实验后，剩余失败才能更有依据地归入模型选点、空间规划、预算不足或复杂绘画能力，而不是继续在“Agent 问题”和“模型问题”之间凭印象来回归因。
