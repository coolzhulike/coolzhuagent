# Part A：尚未裁决的问题（4 项）

## A-1（决策单第 12 项）hook 的"独立授权来源"由谁提供

### 问题
conversation 路径上的外部 shell hook 现在**默认不运行**。要让用户配置的 hook 重新可用，必须先确定"谁有权批准某个 hook 运行、以什么粒度批准"。

### 前因后果
1. 上一轮 A-7b 的核对发现**改前 hook 完全没有独立执行授权**：`run_commands` 只判断"命令列表是否为空"，`PermissionPolicy`/`ToolCaller` 完全不参与 ⇒ **只要配置里出现命令就会 spawn shell**。
2. 同一处还有 **fail-open**：hook 退出码既非 0 也非 2、或**根本起不来**时，只发一条警告，措辞明写 `allowing tool execution to continue`。
3. 第三个缺口：审批在 hook **之前**算好、hook 跑完**原样沿用**，而 hook 位于闸门之后、执行器之前且能产生任意 shell 副作用 ⇒"审批后世界已被 hook 改变、审批仍然有效"。
4. 按裁决 §7.3"没有独立授权和效果边界的外部 hook 不得在高风险路径自动扩张、不加宽松开关"，A-7b 已改为**默认未授权即不运行**（能力名走既有 `with_tool_requirement` 命名空间），并实现"只要 hook 真跑过就重走 `authorize_call` 重判"。
5. **后果**：CLI 的 hook 合并路径（`command-line/src/main.rs:3163→3176`，hooks 来自 `:2787`）没有接线授权来源，而 CLI 不在当时工单的允许范围内 ⇒ **CLI / 子 Agent 的 hook 目前不会运行**，只留一条 "not run" 事实。

### 歧义点（必须由裁决消除）
- 裁决说了"没有独立授权就不放行"，**没有说授权从哪来**：是 settings 里的一个显式字段？每次运行前的一次性用户批准？还是按 hook 内容指纹的信任列表？
- **谁能授权**含糊：如果任何能改 settings 的路径（含模型可写的配置/工具）都能授权，那"独立授权"就退化为"可自我授权"——**这是我建议必须明确堵死的方向**。
- 粒度含糊：按 hook 声明？按命令内容哈希？按会话？按一次性运行？

### 风险评估
| 选项 | 主要风险 |
| --- | --- |
| (a) settings 显式授权字段（按 hook 粒度） | 若字段可被模型/工具写入 ⇒ **自我授权**，等于把任意 shell 执行交给模型（最严重）；需同时规定"授权只能由人在产品界面上改" |
| (b) 每次运行前一次性用户批准（原生确认） | 阻塞式确认会打断长任务；若做成"记住本次会话"，又与 (a) 的信任列表收敛为同一问题 |
| (c) 只对低风险 hook 放行、高风险路径维持禁用 | "低风险"的判定标准需要定义，且判定错误会造成虚假安全感 |
| 维持现状（不放行） | 用户配置的 hook **静默失效**——功能回归，且用户难以知道原因；长期如此会侵蚀"配置即生效"的可预期性 |

### 我的建议
(a) 为最小可行（可审计、可版本化、与既有 `with_tool_requirement` 命名空间一致），并**明确规定授权只能来自产品人工界面**（不得由模型可写路径产生）；随后在 RPR-05c 的原生确认面里补 (b) 作为一次性升级授权。在此之前 CLI 侧维持"按裁决禁用"，并在 UI/日志里明确告知"hook 未运行：缺少独立授权"而不是静默跳过。

### 完成验收口径
1. CLI 下 hook 行为可预期：要么"已授权并运行"、要么"未授权且明确报告未运行"——**不存在静默跳过或静默运行**。
2. 模型可达的任何路径都无法为 hook 授予运行权（有测试证明）。
3. 已有测试 `host_denial_runs_neither_the_pre_hook_nor_the_executor` 等 9 条继续通过。

## A-2（决策单第 13 项）未确认释放互锁的作用域要不要扩到 session / 登录会话

### 问题
"存在未确认的输入释放"这一事实，应该阻断**同一 turn 内**的后续输入（现状），还是阻断更宽的范围（同一会话、同一 Windows 登录会话）？

### 前因后果
1. RPR-04b 让受控 helper 真正产生输入事实：无法确认释放时回执为 `InputReleaseStatus::Unknown`。
2. RPR-05b-1 实现跨 run 互锁：判据 SQL 含 `AND r.turn_id = ?2`，即**只在同一 `(session_id, turn_id)` 内**阻断；解除走可审计的追加事实（`computer_use_release_resolutions` 等两张表，`IF NOT EXISTS` 建表、**不抢 `user_version`**）。
3. 输入所有权的 scope 是 `current_interactive_session_scope()`（= `windows-session-{id}`，整台机器的登录会话）——**两者粒度不一致**。
4. **后果**：用户只要开一个新 turn，就能绕过上一 turn 遗留的未确认释放继续注入输入；而"未确认释放"本质是**桌面级**状态（可能已有按键流到了系统，比如某个 Down 没有对应的 Up）。

### 歧义点
- **未确认释放到底是"某次运行的审计状态"还是"桌面的物理状态"？** 裁决文里把它当作输入安全事实（物理状态），但实现按 turn 维度落地（审计状态）——这个语义分歧是整件事的核心。
- **解除的作用域**是否要随阻断的作用域一起扩大？（扩大阻断但不扩大解除，会让解除无法覆盖全部受影响范围。）
- 同一登录会话下若有多个无关 workspace/房间，扩大阻断会**互相影响**——这是"安全"与"可用"的取舍点。

### 风险评估
| 选项 | 主要风险 |
| --- | --- |
| (a) 扩到 session 维度 | 仍能被"换 session"绕过（若存在多会话入口）；改动小（store + 执行器各一处） |
| (b) 保持 turn 维度 | **新 turn 可绕过隔离**：一次未确认的按键释放可能在后续任意 turn 继续注入——安全缺口 |
| (c) 扩到 Windows 登录会话（与输入所有权对齐） | 最贴合物理语义；但在同一登录会话下、与本次事故无关的任务也会被阻断 ⇒ 可用性下降，且需要明确的"谁能解除"（对应 RPR-05c 的人工恢复入口，**该入口尚未实现**，所以扩大作用域会让"无法解除"的窗口变大） |

### 我的建议
(c) 最贴合语义，但**必须与 RPR-05c 的人工恢复入口一起上线**——否则扩大作用域等于扩大"锁死且无法解除"的范围。若希望先小步走，选 (a) 并同时记录"换 session 可绕过"这一残余风险；(b) 不建议采纳而不记录风险。

### 完成验收口径
1. 新 turn（或更宽作用域）无法绕过未确认释放的阻断。
2. 解除后只允许新 attempt、旧 run 不复活、历史 `unknown` 不被改写。
3. 重启后隔离仍然生效（已由既有测试覆盖）。
4. 若采用 (c)，必须同时提供可用的解除路径（RPR-05c）。

## A-3（决策单第 14 项）原生动作算不算"有模型请求尝试"

### 问题
`StepAction` 作用域要求 `request_attempt_id` 必填，但 CU 执行器没有它的真实来源。**要么改契约，要么 CU 的动作事实永远写不进去。**

### 前因后果
1. 裁决第 1 项要求分作用域校验身份，且**禁止用 `""`/`"unknown"`/`"n/a"`/`"0"`/复制别的维度来凑字段**；"本应存在却缺失"必须报"身份不完整"。
2. 已落地的契约：`RunIdentityScope::StepAction` 的必填维度是 **9 个**（`run_contract.rs:168-179`）：容器五维 + `step_id` + `request_attempt_id` + `tool_call_id` + `action_id`；构造器 `step_action_fact(run_id, step_id, request_attempt_id, action_id)`（`:473-479`）把 `request_attempt_id` 作为**必需参数**。
3. CU 执行器（`computer_use_executor.rs`）里：
   - `ToolCallId` **有**真实来源：`identity.provider_tool_call_id`（CU 由 `computer_use_perform` 这次工具调用发起）。
   - `StepId` **有**：步骤序号/步骤记录。
   - `ActionId` **有**：`computer_use::action_attempt_id(surface, action)`。
   - **`RequestAttemptId` 没有**：执行器不持有"哪一次模型请求尝试产生了这个动作"。用量层（`UsageAttempt{run_id, logical_request_id, attempt_id}`）确实有 attempt 概念，但**没有 plumb 到动作路径**。
4. 现状：**CU 动作回执事实一条都写不进去**（`FactStore::record_action_fact` 会以身份不完整拒收；强写就是伪造）。

### 歧义点
- **"模型请求尝试"这个维度对宿主发起的原生动作是否适用？** 例如：视觉校验时的短时光标移动、恢复流程中的释放动作、用户界面直接触发的点击——它们不是任何一次模型请求产生的。契约的原意（"手动动作不编造模型请求"）与"必填"之间**自相冲突**。
- 若改为可选：**"缺省"与"该动作本应有 attempt 但漏传"如何区分？** 这决定可选化会不会变成一个绕过口子。

### 风险评估
| 选项 | 主要风险 |
| --- | --- |
| (a) 新增宿主侧 scope（如 `NativeAction`，必填容器 + `step_id` + `action_id` + `tool_call_id`） | 契约枚举扩张 ⇒ 所有 `match` 点必须更新（漏改会编译失败，属可控风险）；表达最干净 |
| (b) `StepAction` 内把 `request_attempt_id` 降为可选 | 削弱严格性：**可能被用来把"本应绑定真实请求尝试的动作"写成缺省**；需要配合"缺省仅允许宿主发起的原生动作"这类可校验规则，否则是新的绕过面 |
| (c) 把请求尝试 id 一路 plumb 到动作路径 | 最完整，但改动横跨执行器/planner/用量层，成本最高；当前没有任何消费者需要它 |
| 维持现状（不写 CU 事实） | CU 侧没有任何事实进入业务链 ⇒ "输入安全事实"在桌面路径上缺席，A-5/RPR-04b 的价值只兑现了一半 |

### 我的建议
(b) 最小且语义清楚，但**必须同时给出可校验的区分规则**（例如：`request_attempt_id` 缺省时，`tool_call_id` 必须存在且该动作必须由宿主发起；否则报身份不完整）。若希望更严格、避免"可选即口子"，选 (a)。

### 完成验收口径
1. CU 动作事实能写入，且**身份里没有伪造值**（有测试断言）。
2. 原 Turn 事实不受影响；`validate()` 旧严格语义不变。
3. 现有 `fact_store` 的 22 条测试继续通过。

## A-4（决策单第 15 项）缺会话/轮次维度时 CU 该拒绝执行还是照旧执行但不写事实

### 问题
CU 的身份构造在缺维度时会填入哨兵字符串继续执行。要让事实诚实，必须先去哨兵；但"缺维度"该怎么处置是产品行为决定。

### 前因后果
1. 现状（`main.rs:33952` 一带）：
   `ToolCallIdentity::from_provider(provider_tool_call_id.unwrap_or("provider-call-missing"), caller_session_id.unwrap_or("session-missing"), effective_turn_id)`
   —— 缺会话填 `"session-missing"`，缺轮次则现生成一个 id，**然后照旧执行 CU**。
2. 这是为让 CU 的取消与落库路径继续工作而做的既有兜底；对**日志/取消**它无害，对**事实**它就是伪造维度。
3. 关键风险：`"session-missing"` **不在**契约的占位值黑名单里（`is_placeholder_identity_value` 拒 `""`/`unknown`/`n/a`/`none`/`-`/`0`、控制字符等），因此**它会通过校验并进入事实**——即"缺维度"会以一条看起来合法的会话 id 落库。

### 歧义点
- 缺审计维度时，**能力**（能否执行 CU）与**证据**（能否写事实）哪个优先？裁决反复强调"不写事实不得掩盖已发生的事"，但没说"缺维度时要不要禁止动作发生"。
- 是否需要区分"缺维度"与"值恰为哨兵字符串"？现在两者不可区分（都表现为 `"session-missing"`）。

### 风险评估
| 选项 | 主要风险 |
| --- | --- |
| (a) 缺维度时 CU **拒绝执行**（fail-closed） | **功能回归**：某些调用路径本来就没有 session id（例如未绑定会话的直接调用），CU 会突然不可用；且与"先执行后审计"的既有习惯冲突 |
| (b) 照旧执行但**不写事实**，缺口如实记录 | 事实出现缺口（这是诚实方向，可接受）；前提是**必须去掉哨兵**，否则无法区分"缺维度"与"真有这个 id" |
| 维持现状 | **伪造值进入事实**：违反契约明令，且会污染后续按身份做的所有对账/审计 |

### 我的建议
(b)：执行能力不应因审计维度缺失而丧失；同时**必须把哨兵值从身份里去掉、改为显式 `Option`**，并在事实层记录"因维度缺失未写事实"。需要先检查是否已有消费者依赖 `"session-missing"` 这类字符串（若有，属兼容性风险，需一并处理）。

### 完成验收口径
1. 缺维度时 CU 照旧可执行（行为不回退），但**事实里不出现伪造维度值**。
2. 事实缺口有可查记录（不是静默）。
3. 无消费者因哨兵移除而失效（需先做一次调用者核查）。
