## 第一部分：**阻塞当前执行**（不裁决就无法继续的安全/架构决定）

### 1.1 RD4-02：共享输入安全存储落在哪里

**现象（已核实）**
- `resource_blocking_refs` 的类型是 `&[String]`（`computer_use_store.rs:533`），在 `converge_legacy_run` 里只用于一道判断：资源不安全且**没有任何**非空引用 ⇒ `PreconditionUnmet(ResourceBlockNotEstablished)`，**一个字节都不写**。
- 该引用的实取值 `"input-safety:incident-9"` **只出现在测试夹具**：`computer_use_store.rs:3991/4002`，以及 core-runtime 的 `fact_store.rs:3520`、`run_contract.rs:6443`（后两处经核在 `fn legacy_convergence_candidate()` / `fn legacy_convergence_fact()` 测试夹具内）。
- 全仓**没有**任何 block/incident/safety 语义的建表、**没有**独立库文件常量、**没有**生产者。

**方案阻塞点**
RD4-01 的文档写着它引用"**另一个库**里已建立的阻断记录"且"**不宣称跨库原子性**"（`computer_use_store.rs:2355-2362`）——但那个库在代码里不存在。于是有三个读法，后果互不相同：

| 选项 | 含义 | 后果 |
| --- | --- | --- |
| **A** 新建独立输入安全库 | 例如 `.coolzhu/input-safety.sqlite3`，事故/阻断表 + 单一写入者 | 跨库不可原子 ⇒ 与裁决表述一致；但需定所有权、迁移、备份/清理、打包影响面（属**运维/产品**决定） |
| **B** 复用会话库（同库加表） | 阻断记录与被收敛的 run 同库 | 最省事，但**同库即可原子**，与已冻结的"不宣称跨库原子性"表述**直接矛盾** |
| **C** 承认实际安全根＝内核/进程输入所有权 + 会话库内的释放／未确认事实 | 不建独立阻断库，把引用语义改为引用**既有事实** | 最贴近"**实际**安全根"字面，也解释了"为何不能跨库原子"（OS 不参与 SQLite 事务）；但要改 RD4-01 已冻结的引用语义 |

**背景**：RD4-01 交付了收敛契约与存储层（候选扫描、可重入意图、单事务终态、顺序闸门、幂等/冲突判决），并**刻意**把"阻断从哪来"留成外部引用（`resource_blocking_refs`）。RD4-02 是把这个引用接上真实来源。

**我的建议**：**C 的语义澄清 ＋ 按需选 A**；**不建议 B**（与已冻结表述矛盾）。

**不决策的后果**：v23 迁移已就位但**生产收敛不会运行**，迁移前遗留的"NULL 归属且未收尾"运行会**长期阻断**其 scope（A-1 已核实清理引用数为 0、全 crate 无 sweep 机制）。

**阻塞级别**：**高**（挡 RD4-03）。

### 1.2 RD4-03：谁真正"暂停新输入接纳"、谁签发"恢复协调权"

**现象（已核实）**
- `converge_legacy_run` 的两个前置条件来自**请求参数**：`new_input_intake_paused: bool`（`computer_use_store.rs:526`）与 `recovery_control_authority`。
- 全仓**没有**任何"暂停 CU 输入接纳"的设施；唯一相近的 `local_model_switch_drain_gate`（`main.rs:4472`）是**本地模型切换**排水闸，不作用于 CU 接纳。
- 全仓**没有**任何签发"恢复协调权"的东西。
- 附带事实：`computer_use_runs` **无** `owner_id` 列；owner 需经 `turn_id`/`session_id` ↔ `runtime_runs` 解析（`main.rs:41830` 起的查询面）。目标阶段已有真实运行行可作恢复锚点（`claim_goal_phase_for_dispatch`，`main.rs:42215/42234`）。

**方案阻塞点**：恢复一条遗留运行意味着**写"该运行不再允许继续执行"的状态**。如果我把这两个前置值在编排层写成常量或"调用方声明"，就等于**用待验证对象自证**——第六轮答复 §2.2 明令禁止。所以我在决定前**不实现**编排层。

**需要你定**：① 恢复协调权的**签发者与唯一性**（进程内 mutex 够不够，还是要跨进程锁）；② 恢复期间**暂停接纳的范围**（整个工作区，还是仅受影响 session）。

**不决策的后果**：同 1.1（遗留运行持续阻断其 scope，且**没有**任何恢复路径）。

**阻塞级别**：**高**（挡 RD4-03，也挡"非流式真实接纳"的收尾）。

### 2.1 §C-24：构建期间"声明构建输入被改写"即硬拒绝发布

**现象**：RD4-06 为满足"记录的身份必须对应真正用于构建的输入"，把"构建期间 `cargo build` 改写了 `Cargo.lock`／`tauri.conf.json` 等**声明构建输入**"变成 `[BUILD-INPUT-CHANGED]` **硬拒绝发布**（诊断仍照出，`release_eligible=false`）。

**阻塞点／背景**：这是第六轮 §三 第 7 条的直接后果（"记录的身份必须对应真正用于构建的输入"），但它把"构建时顺手更新锁文件"这一**合法**场景也变成了 fail-closed。

**选项**：① 接受现状（lock 变更即拒绝，需人工确认后重跑）；② 为"锁文件在构建过程中更新"开显式例外（列入允许输入变化），但这就弱化了"输入身份"的强度。

**我的建议**：① 接受现状，但**要求**打包输出把"被改写的输入路径"打印得更显眼（现在已经记进诊断，属可用）。若你要求 ②，请同时给出"允许哪些文件在构建中变化"的白名单口径。

**阻塞级别**：中（不阻塞开发，阻塞"正式发布流程"的顺畅度）。

### 2.2 §C-26：PKG-L07c 的 P1/P0 判定需要外部复核

**现象**：并发导出已修好（锁槽位按"规范槽位目录 + 目标文件名 + package target + profile"、发布权用独占锁文件并保持句柄、消费端也先取读取权）。残留是：**并发中失败的一方仍可能把自己的收据写进共享槽位**（写收据时没有第二次产物核对），且报告里**没有 `generation`**，事后无法自动判定"报告引用的收据是否还是它消费的那一代"。

**阻塞点**：工单**明确说明它未经验性地构造出那一具体交错**，P1 判定建立在代码路径 + 消费侧 fail-closed 实测之上。它自己也请外部复核。

**选项**：① 维持 P1（错配会在消费点 fail-closed、错配产物进不了可发布分区）；② 升级 P0（认定"发布了错配的收据"即不可接受）。

**我的建议**：**升级 P0 并立刻做最小修复**（写收据前再核一次产物内容 + 报告带 `generation`）——因为"收据被错配"正是签名/分发链路最怕的那类事实，且修复成本很小。

**阻塞级别**：中高（阻塞"并发导出能力"的正式验收宣称）。

## 第三部分：需要**技术授权**（改行为会影响既有断言，故我不擅自改）

### 3.1 §C-17：`Saturated` 分支要不要改成"拒绝即故障上报并保留句柄"

**现象**：`park_retained` 的 `Saturated` 分支（最后手段故障态）会"丢登记条目 + 关线程句柄 + 分离线程"，而**读取线程仍存活**并持有管道读句柄与缓冲区。实测该线程在 300ms 内轮数 0→57，写端关闭后才自停。

**背景**：本轮已用"创建线程**之前**预留容量"把该分支挡在正常流程之外；所以它是**故障态**而非可达路径。

**选项**：① 保持现状（故障态仍丢弃）；② 改为"拒绝即故障上报并保留句柄"，让失管读取器不再存在（但会改动既有断言 `retention_limit_is_bounded_and_saturation_is_an_explicit_fault`）。

**我的建议**：②——"表内不超过 8"本身不证明资源有界，而故障态更不该丢句柄。

**阻塞级别**：中（不影响正常路径，影响"资源有界"的验收严格度）。

### 3.2 §C-18：`holds_unreclaimed_reader()` 对 `Saturated` 的语义修正

**现象**：该函数对 `Saturated` 返回 true，语义上应是"**未回收**"而不是"仍被持有"；CU 的 `readers_retained` 会因此把该情形报成 1 而不是 0。本轮**只改了文档口径、未改行为**。

**需要你定**：是否授权改行为（会动既有断言）。

**我的建议**：授权改，并把口径一并写进读出端（否则"内存/句柄占用"的诊断数字会长期偏差 1）。

**阻塞级别**：低中。

### 3.3 §C-21：是否把读取器容量接纳**前移到 helper `spawn` 之前**

**现象**：现在"拒绝"发生在**建流/写 stdin 之前**（因此"不产生任何输入"成立），但 helper 进程**已经 spawn**（随即被杀）。

**选项**：① 维持现状（进程会短暂存在）；② 把 `HelperPipeReadersAdmission::acquire()` 接到 `spawn` 之前（改动 CU 生产接纳顺序，接口已备好）。

**我的建议**：②，理由：容量耗尽是**可预期**的拒绝，可预期的拒绝不该先创建进程再杀。

**阻塞级别**：低中。
