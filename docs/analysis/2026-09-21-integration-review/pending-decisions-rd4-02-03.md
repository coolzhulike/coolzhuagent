## 决策一：共享输入安全存储落在哪里？

### 现象（已核实）

- `resource_blocking_refs` 的类型是 `&[String]`（`computer_use_store.rs:533`），在 `converge_legacy_run` 里仅用于两道判断：
  - 资源不安全且**没有任何**非空引用 ⇒ `PreconditionUnmet(ResourceBlockNotEstablished)`（`:2440-2452`，**一个字节都不写**）；
  - 顺序闸门要求"先建立阻断再写终态"（`:589`/`:614`/`:654`）。
- 全仓搜索：`"input-safety:incident-9"` 只出现在 **测试夹具**（`computer_use_store.rs:3991/4002`、`core-runtime` 的 `fact_store.rs:3520`、`run_contract.rs:6443`）。
- **没有任何** `CREATE TABLE` 含 block/incident/safety 语义；没有独立的库文件常量；没有写入者。

### 方案阻塞点

RD4-01 的文档写明"`resource_blocking_refs` 引用的是**另一个库**里已建立的阻断记录……**不宣称跨库原子性**"（`computer_use_store.rs:2355-2362`）。但那个"另一个库"在代码里并不存在。三种读法各有后果：

| 选项 | 含义 | 后果 |
| --- | --- | --- |
| **A** 新建独立输入安全库 | 例如 `.coolzhu/input-safety.sqlite3`：事故/阻断表 + 单一写入者 | 跨库不可原子 ⇒ 与裁决"不得宣称跨库原子性"一致；但需新库的所有权、迁移、备份/清理与打包影响面，属**运维/产品**决定 |
| **B** 复用会话库（同库加表） | 阻断记录与被收敛的 run 同库 | 可行性最高，但**同库即可原子**，与 RD4-01 文档"另一个库"及裁决"不宣称跨库原子性"的表述**冲突**；且会改变"输入安全根"的语义 |
| **C** 承认"实际安全根"就是内核/进程层 | 真实输入安全根是命名内核 mutex + 进程内 lease + `release_resolutions`/未确认释放事实（会话库内），**故意不建**独立阻断库；`resource_blocking_refs` 改为引用这些既有事实 | 最贴近"实际安全根"字面，且解释了"为何不能跨库原子"（OS 不参与 SQLite 事务）；但需要把 `resource_blocking_refs` 的语义从"另一库记录 id"改成"既有释放/未确认事实的引用"，即**改 RD4-01 已冻结的引用语义** |

### 我的建议

**先做 C 的语义澄清 + 明确 A 的取舍**：若裁决认可"实际安全根＝内核/进程输入所有权 + 会话库内的释放/未确认事实"，则 RD4-02 只需把 `resource_blocking_refs` 改成引用**既有事实**（无需新库）；若要求"阻断必须是独立、可跨工作区共享的记录"，则必须选 **A** 并明确其存储位置与清理策略。**不建议 B**（它与已冻结的"不宣称跨库原子性"表述直接矛盾）。

## 决策二：谁真正"暂停新输入接纳"、谁签发"恢复协调权"？

### 现象（已核实）

`converge_legacy_run` 的两个前置条件来自**请求参数**：

- `new_input_intake_paused: bool`（`computer_use_store.rs:526`，用于闸门 `mark_paused_and_authorized`，`:2365`）；
- `recovery_control_authority`（同一函数，声明值）。

全仓搜索确认：**没有**任何"暂停 CU 输入接纳"的设施（唯一相近的是 `local_model_switch_drain_gate`（`main.rs:4472`），那是本地模型切换用的排水闸，不作用于 CU 接纳）；也**没有**任何签发"恢复协调权"的东西。

### 方案阻塞点

恢复一条遗留运行会**写"该运行不再允许继续执行"**的终态（控制维度），并且可能影响"是否允许开放新输入"（资源维度）。这要求：

1. 暂停新输入接纳必须有**真实实现**（否则收敛期间新输入可能与恢复动作竞争）；
2. 恢复协调权必须有**真实签发者与唯一性**（否则两个恢复实例可同时对同一对象写事实——RD4-01 已用 CAS + 对账键挡住重复写，但"谁有资格发起"没有答案）。

### 我的建议

最小可行且不伪造自证的路径：

- **恢复协调权**：用一个**显式的恢复操作主体**（例如"恢复服务实例 id + 启动时刻 + 独占锁文件/内核 mutex"），并把它作为**输入**传给 `converge_legacy_run`，而不是在编排层里填常量；锁的粒度与位置请你定（进程内 mutex 足够，还是要跨进程）。
- **暂停接纳**：复用 CU 接纳处已有的**输入前检查位点**，把"恢复进行中"作为一个真实的接纳阻断条件（而不是在恢复代码里声明 `true`）。这需要你确认：恢复期间**整个工作区**暂停 CU 接纳，还是只暂停**受影响 session**？

## 若不决策的后果（如实陈述）

- **v23 迁移已就位、但生产收敛不会运行** ⇒ 迁移前遗留的"NULL 归属且未收尾"运行仍会**长期阻断**其 scope（A-1 已核实 `main.rs` 对 `computer_use_runs` 的清理引用数为 0、全 crate 无 orphan/stale/recover/sweep 机制）。
- 这**不是**新风险，而是把裁决已点名的缺口保持显式；RD4-03 的存储层已备好，接线只差上述两个决定。
