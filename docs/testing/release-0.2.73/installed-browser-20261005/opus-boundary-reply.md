**结论：毫秒级的 click 竞争应该转成\"有边界的未覆盖风险\"写进文档，不再阻塞整体回归。没有找到 Agent 必须修的源码问题。** 本轮宿主调用 6 次（列工具 1、glob 1、read 2、grep 2）。

**源码事实（input:177-230）**
- 在同一个 UI 闭包里，mousePressed 和 mouseReleased 连续入队，排 up 之前不等 down 的回调（216-221）。
- 只有两个回调都确认才算 Released；入队失败、闭包排队失败、3 秒超时都记为 ReleaseUnknown，不补发（207、222、226、229）。
- 事件记录和这个结构一致：down 到 up 只隔约 1.3ms，pagehide 在 up 之后约 10ms。

**为什么页面自发导航基本命中不了**
- 这只是推断，我没有读 Chromium 源码。up 在 down 后约 1ms 就已经进了渲染进程的输入队列，而 location.assign 要等网络响应并提交后才会卸载旧文档，几乎总是排在 up 后面。
- 之前那次页面在 pointerdown 里忙等 1600ms，up 也跟着晚了约 1600ms 才到，说明 up 是排在主线程后面等待的。
- 所以在不改生产代码、不拉长 down 的前提下，要合法地增加命中机会几乎没有办法，反复刷轮次也没有意义。

**降级的前提条件**
1. 在文档里写明：这个场景依赖 216-222 行的入队顺序，以及\"状态未知就不补发\"的规则。
2. 每次导航类回归，目标页都要记录第一次 pointermove 的 `buttons` 值，并统计孤立的 up/down 事件。`buttons` 不为 0，或者出现孤立事件，就判失败。
3. 整轮回归中 ReleaseUnknown 必须是 0，出现一次就停下保存轨迹。
4. 风险范围写清楚：浏览器侧发起的替换（跨站换进程、宿主关闭或导航）正好落在这 1ms 里，这种情况没有覆盖。另外，用户在面板里手动导航时不经过执行门，这是历史审查的结论，本轮没有重新核对 browser_panel。

**低成本执行方案**
- **显式 Navigate 覆盖进行中的 window.open**：
  - 测试页的弹窗目标由服务器延迟约 30 秒才响应。这是页面自身的行为，不改生产代码。
  - SWE-2 先 click，等 popup 还在 pending 时再执行 Navigate 到另一个页面。
  - 通过标准：最终停在 Navigate 的目标页；popup 目标页没有显示，也没有收到输入；轨迹显示 popup 序列被作废，输入来源证明不能用在 popup 页上。
- **非 100% 缩放**：
  - 主会话把面板缩放到 125%，这一步标为辅助事件。
  - SWE-2 在 pageY>0 时点击 checkbox。
  - target 里没有任何 zoom/scale 处理（grep 没有命中），所以必须实测。
  - 判定：点对了节点算通过；预检保守地拒绝属于已知局限，可以接受；点到别的节点是阻塞问题，需要停下来，加上\"缩放不等于 1 就拒绝\"的规则后再复测。
