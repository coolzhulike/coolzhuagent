**源码事实**
- **候选窗口的收集条件**：`enum_window_for_hint`（windows_impl:353-366）只检查两点：窗口可见，以及 `matches` 通过。没有检查 owner、扩展样式、DWM cloaked 状态或窗口面积。`unique_window`（window_target:75-81）只要匹配到 2 个及以上就报 Ambiguous，bridge 在 1145 行把它映射成 `target_ambiguous`。
- **这些检查都在任何输入之前**：bridge:69-77 先选窗口，再对前台窗口截图，两者不一致就报 stale。歧义时不会退回到前台窗口，也不会自动取第一个匹配。
- **一个可以排除推测的条件**：`matches` 在给了 window 提示时，要求标题或类名包含提示文字（:57-59）。工具提示窗口通常没有标题。所以如果 X 第四步的 target 带了"无标题 - 画图"这类 window 提示，工具提示窗口就几乎不可能被匹配进来，这个推测基本可以排除。需要先查 X 那一步的 target 字段。

**必须先取到的事实**

歧义时在轨迹里写入每个候选窗口的以下信息，不含标题和路径：
- 类名分类，只用枚举值：tooltip、`#32770` 对话框、other；
- 布尔标志：是否有 owner、TOOLWINDOW、NOACTIVATE、TRANSPARENT、TOPMOST、是否被禁用、DWM 是否 cloaked、面积是否为 0、是否为前台窗口；
- 面积档位；
- 当时使用的 application/window 提示是否为空。

**窄修复的方向（拿到证据后再定）**
- **可以优先考虑排除的**：DWM cloaked 的窗口和面积为 0 的窗口。它们按定义就不可交互，与具体应用无关。Win11 打包应用常有 cloaked 的可见窗口，这同样是候选来源之一，没有证实。
- **再考虑**：同时带 NOACTIVATE 或 TRANSPARENT 的 tooltip 类窗口。
- **不要排除**：有 owner 的窗口、`#32770` 对话框，以及主窗口被禁用、模态对话框打开的情况。这些歧义必须保留。
- **备选**：歧义时只做观察、不发输入，在 300ms 内再枚举一次。它不发送任何输入，但属于有界重试，要你决定是否接受；没有证据显示窗口是瞬时出现的，就不要加。
