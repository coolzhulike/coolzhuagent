**源码已证实**
- **逐项结果没有传给规划**：`parse_visual_verification`（973 行起）只在 evidence 里写 `criteria_met=k/n`，summary 是两句固定的话。`recent_step_feedback`（763–776）只有类别、delivery、effect、goal。`bounded_step_feedback` 只多一个 `subgoal_progress`。所以规划模型拿不到"0 号已满足"这个信息。

- **window-canvas 的坐标容器是整个客户区**：adapters:425 按 `recorded.canvas_rect` 换算，这和 step2 低 y 值落到工具区一致。系统提示第 39–40 行已经写了"含工具栏、候选需对照截图确认"。

**最小修改**
1. **只回传最近一次合法验收，不跨步累积。** 验收本来就是 run_start→current 的比较，最新一次就是累计结果。跨步合并反而会把 S 场景那种 true/false/true 的波动锁成"已完成"。
   - 在 planner 实例里存 `last_visual_criteria{generation, [{index,met}]}`，只在 parse 成功后覆盖；基线不可比时清空。
   - plan 时只有 generation 和当前观察对得上才附上，否则不带。
   - 不放 evidence 正文、引用或坐标，也不持久化。
   - 提示里写明它只是上次验收给的建议，不能当作完成或授权依据。
2. **step 不加 step_number。** step_number 容易让模型把"第 2 步"对应成用户说的"第二步：左眼"，前面一步失败后就会错位。只在系统提示里加一句"step 是从 0 开始的调度计数，与任务子项无关；按未满足的条件和最新截图选择下一步"即可。
3. **坐标**：候选经截图确认后，提示里写成"优先用 UIA 画布引用"，保留 window-canvas，不拒绝。这样 y=0 就是画布顶，不会从工具栏开始算。执行时逐点检查是否落在可见区内，这一点之前建议过，是否已经实现要你核对。

**风险**
- 验收员误判 met=true 时，规划会跳过那一项。最终验收每次都重新判定，所以不会误报成功，但可能浪费步数。
- step1 判 progress=false 是正确的：重复画矩形不算进展。

**归因**
- 已证实的 Agent 缺口：逐项进度没有回传；step 语义没有说明。
- 尚待证实：回传之后模型还会不会重复画、会不会选对引用。这需要在新空白画布上用真实 SWE-2 重跑，截图人工判断和宿主 goal 分开记录。修复后如果仍然重复画或落点错，就记为模型规划能力未达标。
