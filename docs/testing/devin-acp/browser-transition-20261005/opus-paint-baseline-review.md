**结论：设计可以采纳。run_start 只保存图像和几何信息更合适，不要保存完整 Observation。** 本轮我没有调用工具，没有读源码，下面全部基于你给出的事实。

**为什么不存完整 Observation**
- 完整 Observation 里带着起始帧的 UIA 引用和 elements。一旦被提示词或执行路径误用，就会拿旧引用去操作当前界面。
- 建议 run_start 只保存这几项：图像、screen_rect、canvas_rect、窗口身份、DPI，以及截图时刻或帧 ID。不保存 elements，也不能用来构造 FrameRef。
- 内存上每个实例只多一张图，实例结束就释放，可以接受。

**图像顺序**
- 每张图都要有文字标签（start / previous / current），不要只靠位置。如果 ACP 支持图文交错，就把标签紧贴在对应图片前面；不支持的话，提示里要写清楚序号对应关系。
- 去重后（第一步时 start 就是 previous），要写明“图 1 = run_start = previous”，避免模型把两张图的说明套错。
- 三张图的压缩和缩放要一致，否则模型会把压缩差异误判成新笔迹。
- 一次请求的图片数量和大小有没有上限，需要你核实 ACP 的能力协商结果。

**必须守住的语义**
1. criteria 是否满足，只看本次 start→current 的判断。不能把之前某一步的 met=true 累计成完成，否则 S 场景那种 true/false/true 的波动会被误判为完成。
2. image_changed 和 no_progress 只按 previous→current 计算，你已经写了。
3. 如果窗口身份或几何信息变了（移动、缩放、画布滚动），把基线标为不可比。显式的新增条件维持 false 或未证实，但不阻断观察和动作。
4. 确认初始验证时 start 和 current 是同一帧：显式新增条件为 false；存在性条件仍然可以零动作完成。

**未核实的风险**
planner 实例的生命周期必须等于一个 CU job。如果同一个 job 在分段等待或续接时会重建 planner，基线会被重置到中途状态，中途已画的内容就会被当成本轮新增。这一点要你按源码确认。

**验收标准**
- S 类任务里，第一步画的身体在后续每一步都应判为本轮新增。
- 旧人物仍然不能算作本轮新增。
- 截图人工判断和宿主 goal 分别记录。
- 每步视觉验证请求的次数不增加。
