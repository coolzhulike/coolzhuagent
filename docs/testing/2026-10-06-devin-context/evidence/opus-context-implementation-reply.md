**结论：主干设计成立，可以继续做重置实测。有 2 项必须修，2 项需要核实（成立就必修），其余可以延期。** 本轮没有调用工具，只看了你贴的片段，不是完整仓库审查。

**片段里已经确认的**
- **每轮都核旧锁**：处理旧锁的分支已经移到\"上下文是否变化\"的判断之外，稳定绑定下每轮都会检查旧回合是否收尾，并且只释放锁，不归档远端会话。
- **load 失败不偷偷 new**：远端不支持 loadSession，或者 load 失败，都直接报错。回合由 execute 结尾转成 not_sent，游标不推进。
- **重置和换模型都换域**：`context_digest` 里包含 reset 和精确模型 ID，变化时归档旧远端并删除绑定，然后新建会话。
- **completed 的判定**：要求 terminal、end_turn、已排空三者同时成立。不确定的回合只把用户原话（source）记为已知，防止旧指令重放，其它历史不算已导入。prepared 和 not_sent 都不推进游标。
- **增量记录先写、prompt 后发**：这个窗口没有问题。记录失败，或者记录后、发送前出错，状态都会落到 not_sent，被跳过。

**必须修**
1. **删除判定会误报，而且每轮重复。**
   - `removed` 用的是 `known` 减去 `candidate_ids ∪ source_ids`。如果 candidate 受历史窗口或条数限制，消息太旧被挤出来时，就会被误判为\"已删除，不得再据此执行\"。
   - `known` 从不清理已删除的 ID，`take(20)` 又按 ID 排序，结果每轮都会重复报同一批 ID，真正新删除的消息可能永远排不上。
   - 修法：
     - 对 known 里的 ID 直接查 `chat_room_messages` 判断是否存在，不用 candidate 集合来推断；
     - 本轮报过的删除，在 `stamps_json` 里写一条墓碑记录（digest 写成 `deleted`）。等这一轮 completed 之后，从 known 里去掉，不再重复报。
2. **宿主判失败、但协议已经正常结束的回合，会把宿主的结论瞒住。**
   - 生效模型未确认、CU 还在待执行这两种情况，协议都是 end_turn 并且已排空，所以被算作 completed。
   - 如果宿主为这一轮保存的失败提示也通过 `record_replies` 记成了 Devin 自己的输出，下一轮就不会发给远端。远端会以为自己的答复有效，或者以为 CU 任务还在跑。
   - 修法：`execution_failed` 为真的回复不调用 `record_outputs`，让这条失败提示在下一轮作为宿主消息送达。

**需核实，成立就必修**
3. **外部消息有没有作者标签。** delta 只带了 `host_message_id` 和 InputMessage。如果 `input_message_from_persisted` 没有把作者或 agent 写进内容，同聊天室里其它 agent 的 assistant 回复会被远端当成自己说过的话。修法很简单：从已经查出来的 persisted 行里取 author，放进 delta 项。
4. **哪些路径会清锁。** `rotate_idle_context` 只放行 \"unknown 且已排空\" 的旧锁。terminal 和 not_sent（包括 prepare 失败那条路径）一定要在别处清锁，否则下一轮会被永久拦住。宿主在 prepared 或 sent 状态时崩溃，启动时有没有恢复成 unknown 并确认排空，也要实测。

**可以有界延期**
- \"此前未完成回合\"会一直报历史上最后 8 个。建议只报最后一次 completed 之后的。
- 同一个 run 里同一 agent 有多次 attempt 时，outputs 按 run_id 整批归到每一个 completed attempt 上，可能把后面不确定 attempt 的回复也提前算作已知。
- 自动 handoff 后续跳转里产生的 Devin 回复，是不是也走 `record_replies`，并且 `parent_run_id` 和 ACP 的 `scope.run_id` 是否一致：片段里看不出来。如果没走，后果只是下一轮重复导入，不会漏信息。
- `assembly.messages.len()==selected+1`，以及只按本聊天室查询消息：引用转发或注入消息的场景可能被硬拒。这种拒绝是保守的，有实例再放宽。
- CLI 版本变化时直接报错，用户必须手动重置，需要在发版说明里写明。
- 系统说明里如果有每轮都会变的字段，摘要每轮都不同，系统说明就会每轮全量重发。这只影响成本。

**现有证据证明不了的边界**
- 重置和换模型换域：还没有实测。
- 回合取消、但远端没有确认取消时，远端是否已经真正停下：宿主只能证明本地进程已排空。
- 远端旧内容、撤回的记忆、更正前的原文，在物理上都还留在远端历史里。只能靠提示\"作废\"，要彻底清除只能重置。
- 不确定回合的用户原话被永久抑制：它可能根本没送到远端，这是\"宁可不发、也不重复发\"的取舍，需要在界面上提示用户重新发送。
- `delta_history_messages=0` 只在测试过的连续对话和流式回合中成立，不代表 handoff、引用转发、宿主崩溃恢复这几条路径也成立。
