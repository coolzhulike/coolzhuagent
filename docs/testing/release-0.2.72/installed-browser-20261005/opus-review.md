**结论：源码上存在一个能把正常 HTML 句子误拒的结构性缺口。但这次失败是不是由它造成，还没有证实。** 本轮宿主调用 8 次（列工具 1、grep 2、read 5），实际读了 verification 的 1–140 行和 188–213 行，以及 planner 的 850–940 行。

**已证实（源码）**
- `grounded_positive`（verification:48-67）的拼接规则：选中的索引去重排序后必须严格相邻，角色只能是 StaticText 或 InlineTextBox，按顺序拼接后要包含引文。
- 按这条规则推演：如果投影像 Chromium 完整 AX 树那样，输出 `ST"目标页输入事件："`→`ITB(同文)`→`ST"0"`→`ITB"0"`，那么最自然的选法（两个 ST）不相邻，会被拒；只有不自然的 `[ITB_a, ST_b]` 能通过。`<b>` 如果投影成一个空的 generic 节点，也会因为角色检查不通过而断开。
- 交互路径（planner:925 附近）判定未满足时不报错，规划会继续循环，所以最终表现为 budget_exhausted，而不是一个明确的验收拒绝。
- 9 字符、25 字节和"目标页输入事件：0"（全角冒号）的长度一致，但这只是吻合，不能当证据。

- 是不是正好这一项被拒。现有 summary 里已经有 `criteria_met` 和 `ungrounded_positive_count`，可以先查轨迹：如果显示 2 项通过、1 项未落地，基本就是引文落地被拒，而不是裁判模型判错。

**最小修复（证实后再做）**
只放宽拼接时允许跳过的节点，别的都不动：
- 选中节点之间未被选中的节点，只允许两种：名字为空，或者是 InlineTextBox 且名字是它前面最近一个 StaticText 名字的子串（即重复片段）。
- 被跳过的节点不参与拼接。
- 单独存在、带新文字的 ITB 不能跳过，否则会把隔开的两段文字拼成杜撰的句子。
