## 结论边界

本报告记录的是用户反馈后的初始现场，明确身份为已安装的 **0.2.23**，不是 0.2.24，也不代表工作区尚未编译的修改已经生效。原生窗口在启动初期未出现在可控窗口列表中，随后通过已观察到的正式安装入口恢复为可控的 Tauri 窗口；下文分别标注“同服务 IAB 观察”和“原生安装版复测”。

未停止或重启进程，未保存模型配置，未修改 Base URL/API Key，未发送新的模型消息，未删除或修改聊天室内容。诊断期间曾把当前活动聊天室从“验收-20260927”切到“测试环境”；随后再次选择“验收-20260927”，界面顶部提示已回到该房间，但切换请求未收敛，选择器和关闭按钮保持禁用，权限仍为“状态未知”。真实 qwen 配置只被读取；模型发现使用“不使用密钥”选项，结果不能代表密钥可用性。

- 安装版 web-console 进程为 `coolzhu-web-console.exe`，监听 `0.0.0.0:8765`。
- Tauri shell 进程为 `coolzhu-tauri-shell.exe`，窗口标题为 `COOLZHU AGENT 控制台`。
- 更新面板显示当前版本 `0.2.23`，构建标识 `9eae50ebd857`，渠道为正式发行版。
- `@oai/sky` 初始化成功。启动初期 `sky.list_apps()` 只返回已安装的 `COOLZHU CODE Agent` 条目且为 `isRunning:false/windows:[]`；随后通过已观察到的正式安装入口唤起既有壳，`sky.list_windows()` 返回唯一 COOLZHU 窗口：标题 `COOLZHU AGENT 控制台`、Tauri shell、窗口 ID `4720514`。

## 原生同源内嵌浏览器诊断（仍为 0.2.23）

为验证“内嵌控制台占用同源连接”这一待证假说，使用原生浏览器面板自身的地址栏进行了一次可逆清空，未改动模型配置、API Key、聊天室消息或工程文件：

1. 清空前，浏览器地址栏值为 `http://127.0.0.1:8765/`；浏览器预览文档的 URL 也是 `http://127.0.0.1:8765/`，面板文案明确为“已在主面板内嵌”该地址。
2. 通过地址栏输入并打开 `about:blank` 后，预览文档变为 `about:blank`，控制台自身不再嵌在浏览器预览中。
3. 清空后打开并刷新统计，页面从此前的“用量加载失败：Failed to fetch”恢复为“请求 4 · 网络尝试 4 · 失败或中断 0 · 进行中 0 · 用量未完整提供 4”。
4. 清空后打开升级页约 1.5 秒即显示“尚无正式发布版本”，检查按钮可用；点击“检查更新”约 2.2 秒后仍正常收尾，没有 `Failed to fetch` 或禁用卡住。
5. 清空后重新打开设置，仍显示“获取失败：Failed to fetch”，且表单停留在“新会话”和默认 DeepSeek Base URL；因此内嵌页占用可以解释统计和升级的前后差异，但不能单独解释设置读取失败。

清空后用只读系统连接观察仍看到 6 条由 web-console 进程持有的本机 `Established` 连接，因此不能把“清空 iframe”简单等同于连接数归零；这些连接可能来自主控制台或其他长期通道，需后端日志区分归属。

这组前后对照强支持同源内嵌页面或其常驻连接影响统计、升级请求，但还不是完整根因证明；需要 Sol 从后端日志和请求链路确认请求是否到达及失败类型。`@oai/sky` 没有页面脚本、DOM、console 或 network API，故本轮不能从原生窗口直接取得失败请求 pathname、方法或 HTTP 状态。

## 清空内嵌页后的 qwen 配置与模型发现复核（仍为 0.2.23）

这一步是对上面初始失败记录的追加复核，不能覆盖初始 0.2.23 失败身份：

1. 关闭内嵌 `8765` 页面后，重新打开设置并重新选择已保存的 `qwen · qwen3.8-flash`。界面显示“配置已载入”，Base URL 恢复为已保存的阿里百炼地址，模型 ID 为 `qwen3.8-flash`；未输入、读取或输出 API Key，也未保存表单。
2. 选择 qwen 后原先的“获取失败”文案消失。结合前端错误前缀，它属于远程模型目录发现状态，不是本次 qwen 配置读取失败；配置读取成功提示为“配置已载入”。
3. “此次查询不使用密钥”复选框经原生截图确认未勾选，随后点击“获取模型”走已保存密钥的真实查询。约 4.5 秒后显示“阿里百炼 · 已获取 261 个模型”，发现项为 `qwen3.8-flash — 支持图片输入`。该动作未更改保存配置。
4. 本轮曾在误点设置窗口“关闭”按钮后使原生壳窗口退出；后端服务随后由正式安装入口恢复，未改动代码。随后在新建的受控聊天室“聊天07”中确认唯一发送对象为 qwen，发送了简短输入类型询问。真实 qwen 约 7.4 秒返回可接收纯文本、文件路径/内容、图片等多媒体、代码片段、URL 和查询请求等类型的说明；没有要求或返回系统提示内容。受控聊天室截图保存在 `tmp/real-acceptance-20260928-qwen-controlled-023.jpg`，不含原有私聊记录。
5. 受控房间统计随后成功显示 qwen `1 次请求`、`网络尝试 1`、`失败或中断 0`、`进行中 0`；已知输入 4,594、已知输出 240 token。统计截图保存在 `tmp/real-acceptance-20260928-qwen-stats-controlled-023.jpg`。这证明清空内嵌页后的旧安装版真实 qwen 链路和统计可完成，不能替代代码冻结后的新安装版验收。
6. 验收结束后已通过原生聊天室选择恢复原活动房间“验收-20260927”，权限重新显示“完全访问”，发送对象恢复为 qwen；受控房间“聊天07”未删除，便于保留证据。

## 交付判断

本报告不是通过报告。当前安装版仍是 0.2.23；原生复测仍显示发送对象结构、设置职责、聊天室切换、统计和升级检查存在失败或卡住。代码修改、构建、安装并完成真实 qwen3.8-flash 矩阵前，不应宣称 0.2.24 入口修复完成。
